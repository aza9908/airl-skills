# airl-hub — хаб руководителя

Хаб — это не ещё один сервис, а **оболочка**: вход, шапка, экран руководителя
и реестр сервисов. Каждый отдел живёт по своему пути (`/sales`, `/marketing`, …),
деплоится отдельно и может упасть, не уронив остальных.

```
                     hub.company.kz  (один домен, один TLS, один вход)
                                 │
                       обратный прокси (Caddy / Nginx — готовит /airl-vps)
     ┌──────────────┬────────────┼─────────────┬──────────────┬─────────────┐
     /              /auth        /marketing    /sales         /hr           /finance
   оболочка хаба   провайдер    сервис        сервис         сервис        сервис
   + экран CEO     входа        отдела        отдела         отдела        отдела
     │                              │             │              │             │
     └── читает /healthz и /api/hub/summary каждого сервиса ─────┘             │
                                    └──── все читают core/metrics, пишут mart_<свой> (DWH)
```

## Шаг 0. Определи режим

| Что видишь | Режим |
|---|---|
| Репозиторий хаба пуст или в нём только `COMPANY_MAP.md` | **A. Создать хаб** |
| Человек в репозитории сервиса, есть `airl.service.json`, или сказал «подключить X» | **B. Подключить сервис** |
| «готовность», «Demo Day», «статус», или в реестре уже есть сервисы | **C. Сводка готовности** |

Скажи человеку одной фразой, какой режим и почему.

Вопросы — по одному, 3–4 варианта, рекомендация и почему. Ответ «не знаю» —
бери рекомендацию и скажи об этом.

---

## Режим A. Создать хаб (один раз на компанию)

Обычно делает команда AIRL вместе с руководителем. Скажи в начале: соберём оболочку,
в которую на неделе 4 встанут сервисы всех отделов — вход, шапка, экран руководителя.
Сервисы отделов при этом не трогаем.

### Перед стартом

Прочитай `COMPANY_MAP.md` (разделы 6–9). Нет карты — остановись, нужен `/airl-spec`.
Проверь, что сервер и домен готовы (`/airl-vps`) — если нет, хаб можно собрать
локально, но подключение сервисов будет на временных адресах.

### Вопросы

1. **Провайдер входа** — один на весь хаб. Рекомендация зависит от карты:
   - ПДн граждан РК и требование хранить в Казахстане → свой провайдер на сервере
     в РК: Authentik, Keycloak или Zitadel (рекомендую Authentik — проще в
     настройке, есть вход через Google/Microsoft и двухфакторка);
   - хранилище уже на Supabase в подходящем регионе → Supabase Auth;
   - у компании Google Workspace / Microsoft 365 → вход через них поверх провайдера.
   Провайдер выдаёт токен (JWT) с полями `sub`, `email`, `role`, `department`;
   публичный ключ доступен по JWKS. Роли — строго из раздела 7 карты.
2. **Маршруты** — пути на одном домене `hub.company.kz/sales` (рекомендую: одна cookie
   входа, один сертификат, нет проблем с CORS) · поддомены `sales.hub.company.kz`
   (нужна cookie на родительский домен и CORS — сложнее).
3. **На чём оболочка** — тот же стек, что у сервисов отделов (смотри их репозитории),
   чтобы её мог поддерживать любой участник курса.

### Что собрать

Строго по частям, после каждой — что открыть и нажать, и стоп до «дальше».

- [ ] **Часть 1. Реестр** `hub/services.json` — пустой массив сервисов с полями из
  `airl.service.json` плюс `status` (`ready | connected | degraded | disabled`),
  `upstream` (внутренний адрес сервиса), `connected_at`, `checked_by`.
- [ ] **Часть 2. Вход.** Провайдер настроен, роли из карты заведены группами,
  оболочка требует вход, выход завершает сессию. Тестовые пользователи на каждую
  роль: `ceo`, `head_<отдел>`, `staff_<отдел>`.
- [ ] **Часть 3. Оболочка** — PWA в токенах раздела 9 карты (те же правила, что
  в `/airl-pwa`): шапка с логотипом, переключатель сервисов (показывает только
  сервисы, которые разрешены роли), профиль и выход. Устанавливается на телефон —
  это **единственное** приложение, которое сотрудники ставят на экран.
- [ ] **Часть 4. Экран руководителя.** По плитке на сервис: название, 2–4 показателя
  со светофором и сравнением с прошлым периодом, предупреждения, время обновления,
  переход в сервис. Сверху — сводная строка по отделам.
  Правила:
  - сервер оболочки опрашивает `/api/hub/summary` каждого сервиса **параллельно**,
    с таймаутом 3 с, пересылая токен текущего пользователя (сервис сам решает, что
    этой роли показать) и кэширует ответ на 60 с на пользователя;
  - сервис не ответил → плитка «Нет данных от сервиса · обновлено в …» серым, а не
    падение всего экрана;
  - число форматируется по-русски (`48 250 000 ₸`), подпись показателя — из карты,
    а не из ответа сервиса, чтобы названия везде совпадали;
  - `head_<отдел>` видит экран только со своим отделом, `staff` — сразу свой сервис.
- [ ] **Часть 5. Маршрутизация.** Конфиг прокси генерируется из реестра — один блок
  на сервис. Пример Caddy:

  ```caddyfile
  hub.company.kz {
      encode zstd gzip
      header {
          Strict-Transport-Security "max-age=31536000"
          X-Content-Type-Options nosniff
          Referrer-Policy strict-origin-when-cross-origin
      }
      handle /auth/*      { reverse_proxy authentik:9000 }
      handle /sales/*     { reverse_proxy sales:3000 }
      handle /marketing/* { reverse_proxy marketing:3000 }
      handle              { reverse_proxy hub-shell:3000 }
  }
  ```

  Сервис не снимает префикс пути сам по себе: он собран под свой `base_path`
  (это проверяется в режиме B). Перезагрузка прокси — без остановки
  (`caddy reload` / `nginx -s reload`).
- [ ] **Часть 6. Журнал хаба** — кто входил, кто открывал какой сервис, ошибки
  опроса сервисов. Без ПДн, кроме идентификатора пользователя.

Положи в репозиторий хаба `HUB.md`: как устроено, как добавить сервис, как откатить,
кто отвечает. Обнови раздел 8 карты, если что-то уточнилось (через `/airl-spec`).

## Режим B. Принять и подключить сервис отдела

Скажи в начале: сейчас проверим, что сервис отдела готов стать частью хаба, и
подключим его. Проверка строгая, потому что одна ошибка в одном сервисе видна
руководителю на общем экране. Красное — объясню, что именно и каким навыком
это исправить.

### Перед стартом — собери

- из репозитория сервиса: `airl.service.json`, `SPEC.md`, `SECURITY.md`, отчёт
  `/airl-code-review-2.0`, адрес, где сервис выложен `/airl-launch`;
- из репозитория хаба: `COMPANY_MAP.md`, `hub/services.json`.

Не хватает чего-то из списка — это уже первая красная строка проверки, а не повод
пропустить пункт.

### Проверка — ворота в хаб

Сначала автоматическая часть. Скрипт лежит рядом с этим навыком
(`~/.claude/skills/airl-hub/scripts/check_service.py`, только стандартный Python 3):

```bash
python3 ~/.claude/skills/airl-hub/scripts/check_service.py \
  --service airl.service.json \
  --map ../hub/COMPANY_MAP.md \
  --registry ../hub/hub/services.json \
  --url https://hub.company.kz
```

Для проверки `/api/hub/summary` скрипт берёт токен тестового пользователя `ceo` из
переменной окружения `AIRL_HUB_TOKEN` (попроси человека выставить её у себя, значение
не печатай). Без `--url` проверяются только файлы.

Затем ручная часть. Итог — таблица:

| № | Ворота | Как проверяем | Итог |
|---|---|---|---|
| 1 | Контракт | `airl.service.json` валиден, `id` есть в разделе 6 карты, `base_path = /<id>` | скрипт |
| 2 | Та же карта | `map_version` сервиса = версии карты | скрипт |
| 3 | Одни цифры | все `hub.metrics` есть в разделе 4 карты; в коде нет своей формулы для них (поиск по коду: расчёт выручки/конверсии вместо чтения из `metrics`) | скрипт + код |
| 4 | Свой участок | `data.writes` = только `mart_<id>`; отчёт безопасности подтверждает права в базе | файл + SECURITY.md |
| 5 | Один вход | нет своей формы входа; токен хаба проверяется на сервере | SECURITY.md + запрос без токена → 401 |
| 6 | Безопасность | `SECURITY.md`: «можно подключать — да», нет СРОЧНО, дата не старше 14 дней | файл |
| 7 | Код-ревью | отчёт `/airl-code-review-2.0` без блокирующих замечаний | файл |
| 8 | Живой | `/healthz` → `status: ok`, версия совпадает с выложенной | скрипт |
| 9 | Отдаёт в хаб | `/api/hub/summary`: форма верна, числа — числа, время с поясом, ответ < 1 с | скрипт |
| 10 | Роли | под `staff` чужого отдела сервис и summary недоступны | вручную, тестовый пользователь |
| 11 | PWA | открывается в оболочке хаба с телефона, шапка хаба, токены дизайна | вручную |
| 12 | Откат | `/airl-launch` откатывает на прошлую версию одной командой — проверено хотя бы раз | лог запуска |
| 13 | Готовность из ТЗ | все пункты `SPEC.md` раздел 10 отмечены и проверены | файл + вручную |

Любая красная строка в воротах 1–9 — сервис **не подключается**. Красное в 10–13 —
подключить можно со статусом `degraded` только с согласия руководителя и с датой
исправления. Для каждой красной строки напиши, каким навыком чинить
(`/airl-spec`, `/airl-dwh`, `/airl-pwa`, `/airl-cybersecurity`, `/airl-launch`,
`/airl-code-review-2.0`).

### Подключение (только после зелёных ворот 1–9 и «да» человека)

1. Добавь сервис в `hub/services.json` со статусом `connected`, `upstream`,
   `connected_at`, `checked_by: airl-hub`.
2. Добавь блок маршрута в конфиг прокси, проверь конфиг (`caddy validate` /
   `nginx -t`), перезагрузи без остановки. На боевом сервере — только с явного «да».
3. Включи плитку на экране руководителя.
4. **Проверка вживую** под тремя пользователями:
   - `ceo` — видит плитку отдела с цифрами, переходит в сервис без повторного входа;
   - `head_<отдел>` — видит свой отдел, не видит чужие;
   - `staff_<чужой отдел>` — не видит сервис в переключателе, прямой адрес даёт 403.
5. Сверь одну цифру с источником правды (например, выручка за прошлый месяц
   против отчёта 1С) — это самый убедительный момент на Demo Day.
6. Закоммить изменения реестра и прокси в репозиторий хаба отдельным коммитом
   «hub: подключить <id> v<version>» — так откат подключения тоже одна команда.

### Отчёт HUB_CHECK.md (в репозитории сервиса)

```markdown
# Приёмка в хаб — «[Сервис]» v[версия]

**Дата**: ГГГГ-ММ-ДД · **map_version**: 1.0 · **Решение**: подключён / не подключён / degraded до [дата]

| № | Ворота | Итог | Комментарий / чем чинить |
|---|---|---|---|

## Проверка вживую
| Пользователь | Ожидали | Получили |
|---|---|---|

## Сверка цифры с источником
[показатель, период]: хаб [значение] · 1С [значение] · совпадает / расходится на [...]

## Что осталось до Demo Day
- ...
```

## Режим C. Сводка готовности к Demo Day

Пройди реестр и карту, для каждого отдела из раздела 6 карты:

| Отдел | ТЗ | Данные | PWA | Защита | Ревью | В хабе | Боль: было → стало | Что мешает |
|---|---|---|---|---|---|---|---|---|
| Продажи | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | отчёт 4 ч/нед → 0 | — |
| HR | ✔ | ✔ | ✔ | ✖ СРОЧНО | — | — | — | роли не проверяются на сервере → `/airl-cybersecurity` |

Опрашивай `/healthz` всех подключённых сервисов. Внизу — три строки: сколько
отделов в хабе, у кого риск не успеть, и что сделать сегодня. Для Demo Day предложи
порядок показа: открыть хаб под `ceo` → общий экран → по отделу: боль, «было → стало»
из `SPEC.md` раздел 1, живое главное действие, сверка цифры с 1С.

## В конце

- режим A: что собрано, адрес хаба, тестовые пользователи (без паролей в чате),
  следующий шаг — подключать сервисы отделов режимом B;
- режим B: решение по сервису, ссылка на `HUB_CHECK.md`, что починить и каким навыком;
- режим C: таблица готовности и план на сегодня.

## Чего не делать

- Не подключать сервис с красными воротами 1–9, даже «временно».
- Не править код сервиса отдела из режима B: только описывать, что исправить и каким
  навыком. Хаб принимает, а не переписывает.
- Не заводить в хабе свои формулы показателей — подписи и определения только из карты.
- Не делать отдельный вход для какого-либо сервиса.
- Не позволять одному упавшему сервису ронять экран руководителя.
- Не перезагружать боевой прокси и не менять боевой реестр без явного «да».
- Не печатать токены, пароли тестовых пользователей и персональные данные.
