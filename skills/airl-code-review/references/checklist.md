# Ручной разбор: что смотреть по областям

Для каждой области: вопросы, как быстро найти проблемные места, и какая важность
по умолчанию. Важность можно поднять, если риск касается денег, персональных данных
или руководителя на экране хаба, и опустить, если код не используется на главном пути.

Поиск по коду — `rg` (ripgrep) или `grep -rn`; папки `node_modules`, `.venv`, `dist`
исключай.

## 1. Корректность и граничные случаи

Возьми главное действие из `SPEC.md` раздел 4 и пройди его в коде от кнопки до базы.

- Пустой список, один элемент, тысяча элементов; пустая строка, пробелы, очень длинный
  текст, эмодзи, кириллица и латиница вперемешку.
- Числа: ноль, отрицательное, дробное; **деньги — не в `float`**: в базе `numeric`/`decimal`,
  в коде целые копейки/тиыны или десятичный тип. Округление — одно правило на весь продукт.
- Даты и время: хранится с часовым поясом (`timestamptz`), граница дня и месяца считается
  в поясе компании, а не сервера. Отчёт «за месяц» 31-го в 23:30 по местному времени.
- Двойное нажатие и повторная отправка формы: создаётся одна запись, а не две.
- Одновременная правка двумя людьми: последняя запись молча затирает первую? Для заказов,
  остатков и денег — блокирует; для заметок — важно.
- Статусы: из любого ли статуса можно попасть в любой? Переходы проверяются на сервере.
- Показатели в хабе: читаются из `metrics`, а не считаются своей формулой (ворота 3).

Блокирует: неверные деньги или показатели, дубли при повторе, падение главного экрана.

## 2. Данные и миграции

**Правило expand → migrate → contract.** Во время выкладки какое-то время работают
старая и новая версии кода, а откат возвращает старую. Поэтому каждая миграция должна
быть совместима с кодом, который сейчас работает:

1. **Expand** (расширить): добавить новую колонку или таблицу, без `NOT NULL` и без
   удаления старого. Старый код её не замечает.
2. **Migrate** (перейти): новый код пишет в оба места или читает новое с запасным
   вариантом; отдельная задача переносит старые данные **партиями** (backfill:
   по 1000–10000 строк, с паузой, с возможностью продолжить с места остановки).
3. **Contract** (сузить): следующим релизом, когда старый код нигде не работает,
   а перенос проверен, — удалить старое и добавить ограничения.

Переименование колонки = добавить новую + писать в обе + перенести + удалить старую.

Проверь:

- миграции в git и выполняются одной командой (`scripts/migrate.sh` для CI и сервера);
- миграция с изменением данных — в транзакции; `CREATE INDEX CONCURRENTLY` —
  наоборот, **вне** транзакции (большинство инструментов требуют отдельную миграцию);
- повторный запуск миграций ничего не ломает (инструмент ведёт таблицу версий);
- фоновые задачи и импорт **идемпотентны**: повторный запуск за тот же день не задваивает
  (`INSERT ... ON CONFLICT`, уникальный ключ источника, отметка «обработано»);
- у таблиц есть первичный ключ; у внешних данных — уникальный ключ источника;
- удаление данных — мягкое (`deleted_at`), если в `DWH.md` записан аудит;
- `DOWN`-миграции не считаются планом отката: откат — это предыдущая версия кода
  на расширенной схеме и копия базы.

Блокирует: миграция ломает работающую версию; перенос данных одним `UPDATE` на большой
таблице; задача, которая задваивает при повторе; удаление без копии.

## 3. Безопасность

Это не замена `/airl-cybersecurity`, а проверка, что новый код не открыл старое.

- Каждый серверный обработчик, который читает или меняет данные, проверяет **вход и роль
  на сервере**. Скрытая кнопка в интерфейсе — не проверка.
- **IDOR** (подмена id): `GET /orders/123` → сервер проверяет, что заказ 123 принадлежит
  пользователю или его отделу. Найди все обработчики с id в адресе и проверь каждый.
- Ввод проверяется на сервере (схема: zod, pydantic); запросы к базе — параметризованы,
  никакой склейки строк с вводом пользователя.
- Ключи — только из переменных окружения; в репозитории — `.env.example` без значений.
- Персональные данные (`SPEC.md` раздел 9, `pii` в `airl.service.json`) не пишутся в логи,
  тексты ошибок, аналитику и в `/api/hub/summary`. Поищи `console.log(user`, `print(request`,
  `logger.info(` рядом с телефоном, e-mail, ИИН/ПИНФЛ/паспортом.
- Загрузка файлов: тип и размер ограничены, файлы не отдаются по угадываемому адресу.
- Ошибки наружу — без стека и путей.

Блокирует: доступ к чужим данным, ключ в коде, персональные данные в логах. Найдено
системное (роли не проверяются вообще) — отправляй на `/airl-cybersecurity`.

## 4. Производительность

Ориентир — данные через год (`DWH.md`, объём и рост), умноженные на 3.

- **N+1**: запрос к базе внутри цикла по строкам (`for ... await db.query`, ленивые связи ORM
  в шаблоне). Решение: один запрос с `JOIN` или `IN (...)`, `include`/`selectinload`.
- **Индексы под запросы экранов**: для каждого главного экрана выпиши `WHERE` и `ORDER BY`
  его запроса — нужен индекс по этим колонкам. Проверка: `EXPLAIN ANALYZE` на копии
  с реалистичным объёмом; `Seq Scan` по большой таблице на главном экране — важно.
- **Постраничный вывод**: ни один список не отдаёт «всё». Лимит по умолчанию и максимум
  на сервере; для длинных лент — по ключу (`WHERE id < :last`), а не `OFFSET 100000`.
- **Таймауты** на каждый внешний вызов (HTTP, модель ИИ, 1С): 5–10 секунд, не «бесконечно».
  Таймаут запроса к базе (`statement_timeout`) для веб-запросов.
- Тяжёлое (отчёты, выгрузки, рассылки) — в фоне, а не в обработчике запроса.
- Показатели хаба — из готовых витрин; `/api/hub/summary` быстрее 1 секунды.

Блокирует: главный экран заметно тормозит уже на тестовых данных; список без лимита
по таблице, которая будет расти. Остальное — важно.

## 5. Надёжность

- Повторы внешних вызовов: только для безопасных операций или с ключом идемпотентности,
  с ограничением числа попыток и паузой, растущей с каждой попыткой.
- **Ключ идемпотентности** на каждую запись во внешнюю систему (оплата, 1С, SMS):
  повтор того же запроса не создаёт второй платёж или документ.
- **Outbox** для внешних записей: сначала в своей базе в одной транзакции с делом —
  строка «надо отправить», потом отдельный процесс отправляет и отмечает «отправлено».
  Так сбой между «сохранили» и «отправили» не теряет и не задваивает. Сложные
  интеграции (1С, банк, маркетплейсы) — `/airl-integrations`, инженерный трек AIRL.
- Входящие вебхуки: проверка подписи, повтор того же события обрабатывается один раз.
- Падение внешнего сервиса не роняет весь экран: показываем, что есть, и понятную ошибку.
- Процесс корректно завершается по сигналу остановки (выкладка без обрыва запросов).

Блокирует: возможен двойной платёж или двойной документ во внешней системе.

## 6. Наблюдаемость

- `/healthz` отвечает без входа, отдаёт `status` и `version`; проверяет, что база доступна,
  но не делает тяжёлых запросов.
- Логи — в формате JSON одной строкой: время, уровень, сообщение, id запроса,
  id пользователя (не ФИО и не телефон). Без персональных данных и ключей.
- Ошибки не глотаются: `catch` без записи в лог — находка. Неожиданные ошибки уходят
  в систему учёта ошибок (Sentry/GlitchTip — см. `/airl-devops`).
- Фоновые задачи пишут «начал / закончил / сколько обработал / ошибка», чтобы зависание
  было видно.

Блокирует: нет `/healthz`. Остальное — важно.

## 7. Тесты

Минимальный набор — в `SKILL.md`. Как проверить, что тесты настоящие:

- тест падает, если сломать то, что он проверяет (поменяй условие — покраснел?);
- тесты ролей идут через HTTP к серверу, а не вызывают функцию в обход проверки входа;
- сквозной тест Playwright работает против собранного продукта на тестовой базе:

```ts
// e2e/main-path.spec.ts
import { test, expect } from '@playwright/test';

test('менеджер создаёт заказ и видит его в списке', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Почта').fill(process.env.E2E_MANAGER_EMAIL!);
  await page.getByLabel('Пароль').fill(process.env.E2E_MANAGER_PASSWORD!);
  await page.getByRole('button', { name: 'Войти' }).click();
  await page.getByRole('button', { name: 'Новый заказ' }).click();
  await page.getByLabel('Сумма').fill('15000');
  await page.getByRole('button', { name: 'Сохранить' }).click();
  await expect(page.getByText('15 000')).toBeVisible();
});
```

- тест ролей (пример на Python, тот же смысл на любом стеке):

```python
def test_manager_cannot_read_foreign_order(client, manager_token, foreign_order_id):
    r = client.get(f"/api/orders/{foreign_order_id}", headers={"Authorization": f"Bearer {manager_token}"})
    assert r.status_code in (403, 404)
```

- миграции на копии: восстановить свежую обезличенную копию во временный контейнер
  (`/airl-devops`, часть 5), прогнать `scripts/migrate.sh`, открыть главный экран
  на этой базе, прогнать миграции второй раз — изменений нет.

Признаки ненастоящих тестов (каждый — «важно»):

- **проверяют заглушку, а не результат**: `expect(mockApi).toHaveBeenCalled()` без проверки
  того, что вернул сервис. Заглушки — только на границе (внешний API, время, случайность);
- **методы «только для тестов»** в рабочем коде (`_resetForTesting`) — вынести в помощники тестов;
- **заглушка без понимания**: подменили функцию, у которой был нужный побочный эффект
  (запись в базу, кеш), и тест проходит, потому что ничего не делает;
- **неполная заглушка**: в фальшивом ответе нет полей, которые есть в настоящем, — тест
  зелёный, а в бою падает; формируй фальшивые ответы из реального образца;
- **тесты дописаны после и подогнаны под код**: если тест не падал ни разу, сломай условие
  и убедись, что он краснеет.

Покрытие строк — ориентир: ниже 40% на серверной части — важно, но 90% без тестов
ролей хуже, чем 50% с ними.

## 7а. API

Для сервисов с API (свой продукт, сервис отдела, `/api/hub/summary`):

- **единый формат ошибки** на все эндпоинты, например
  `{"error": {"code": "VALIDATION_ERROR", "message": "…", "details": [{"field": "email", …}]}}`
  или RFC 7807 (`application/problem+json`). Стек, SQL и пути к файлам в ответ не попадают;
- **коды ответа по смыслу**: 400 — неверный запрос, 401 — не вошёл, 403 — нет прав,
  404 — нет записи (или чужая — тогда тоже 404), 409 — конфликт (повтор, устаревшая версия),
  422 — не прошла проверка полей, 429 — слишком часто, 5xx — только ошибки сервера.
  `200` с `{"ok": false}` — «важно»;
- **списки с ограничением**: каждый эндпоинт списка принимает `limit` (с потолком, например 100)
  и курсор или `offset`; без них — «блокирует», если таблица растёт (заказы, визиты, журнал);
- **повторяемые записи**: POST, который создаёт платёж, заказ или сообщение, принимает ключ
  идемпотентности (`Idempotency-Key`) или проверяет уникальность по бизнес-ключу;
- **проверка входа на сервере** по схеме (zod, pydantic): типы, длины, диапазоны, перечисления;
  лишние поля отбрасываются, а не пишутся в базу;
- **версия в пути или заголовке**, если API читает кто-то кроме своего фронтенда
  (хаб, интеграции): ломающие изменения — только в новой версии, старая живёт до переезда
  всех читателей;
- **описание API** (OpenAPI или раздел в README) есть для эндпоинтов, которые читают другие
  сервисы, и совпадает с кодом.

## 8. Состояния экранов

Из `/airl-pwa`: у каждого экрана со списком или данными есть **пусто** (что сделать
первым), **загрузка** (скелет, а не белый экран), **ошибка** (что случилось и что
нажать), **нет сети** (последние данные с временем обновления). Проверь в браузере:
DevTools → Network → Offline и Slow 3G; сервер вернул 500 — что видит человек?

Ещё: кнопка блокируется на время отправки (защита от двойного нажатия), сообщения
об ошибках на языке пользователя, без технического текста.

Блокирует: на главном экране при ошибке или без сети человек видит пустоту или
бесконечную загрузку и не понимает, сохранилось ли действие.

## 9. Сопровождение

- Адреса, ключи, лимиты, флаги — в переменных окружения, перечислены в `.env.example`.
  Адрес сервера или домен, зашитый в код, — важно (блокирует, если мешает staging).
- Мёртвый код (неиспользуемые функции, закомментированные блоки, старые файлы `*_old`) —
  потом; если путает в главном пути — важно.
- Функции длиннее одного экрана на главном пути, дублирование расчётов — важно, если
  расчёт денег или показателей есть в двух местах.
- `README` или `DEVOPS.md`: как запустить локально, как прогнать тесты и миграции.
- Версии зависимостей зафиксированы файлом блокировки.
- Понятные имена: через месяц другой человек поймёт без автора.
