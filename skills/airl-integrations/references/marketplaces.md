# Маркетплейсы: заказы, остатки, цены

Справочник `/airl-integrations`. Типовые требования: видеть заказы со всех площадок
в одном месте, не продавать то, чего нет на складе, держать цены согласованными,
считать выручку и комиссию по каналу. Все адреса API, лимиты и форматы —
**проверить в документации площадки**; доступ к API выдаётся в кабинете продавца
и бывает не у всех типов продавцов.

## Площадки

| Площадка | Страна | Что известно | Проверить |
|---|---|---|---|
| Kaspi магазин | KZ | есть API для продавцов: заказы и их статусы; товары и остатки исторически — через прайс-лист (XML), который Kaspi забирает по ссылке | актуальный адрес и версию API, токен в кабинете продавца, как сейчас обновляются остатки (API или прайс-лист), лимиты |
| Halyk Market | KZ | кабинет продавца | наличие и состав API — уточнить у площадки |
| Uzum Market | UZ | кабинет продавца, есть API для продавцов | адрес, методы заказов/остатков/цен, токен — проверить в документации |
| Ozon | KZ, UZ и др. | Seller API: товары, остатки, цены, отправления (FBS/FBO); ключи `Client-Id` и `Api-Key` | методы и версии, лимиты, работа с продавцами из KZ/UZ |
| Wildberries | KZ, UZ и др. | API продавца с токенами по категориям (контент, цены, заказы, статистика) | какие токены нужны, лимиты, модели FBS/FBO |

## Главная идея: площадка — канал, а не клиент

- В `core` заказ с площадки — это заказ **канала** (`channel = 'kaspi'`),
  покупатель — клиент площадки. В 1С контрагент обычно сама площадка (договор
  комиссии или агентский) — как именно, **решает бухгалтер клиента**.
- Персональные данные покупателя (имя, телефон, адрес доставки) берём только если
  мы сами доставляем; храним по профилю страны и удаляем после закрытия заказа
  по сроку, согласованному с юристом. Для показателей они не нужны.
- Выручка канала — по отчётам площадки (продажи, возвраты, комиссия, логистика,
  выплаты), а не по сумме заказов. Определение — в разделе 4 карты.

## Таблица соответствия SKU

Без неё интеграция не работает. Ведёт клиент (товаровед), мы — проверяем.

```sql
CREATE TABLE IF NOT EXISTS int_sku_map (
    marketplace     text    NOT NULL,          -- 'kaspi', 'ozon', 'wb', 'uzum'
    mp_sku          text    NOT NULL,          -- артикул/offer_id на площадке
    mp_product_id   text,                      -- ID карточки на площадке, если есть
    sku             text    NOT NULL,          -- наш SKU (ключ в 1С/core)
    units_per_mp    integer NOT NULL DEFAULT 1 CHECK (units_per_mp > 0),  -- набор из N штук
    active          boolean NOT NULL DEFAULT true,
    min_price       numeric(18,2),             -- ниже не публикуем
    updated_at      timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (marketplace, mp_sku)
);
```

- Заказ с SKU площадки, которого нет в таблице, — не угадываем: строка в отчёт
  «неизвестные SKU», заказ виден с пометкой.
- Один наш SKU на нескольких площадках — нормально; один SKU площадки на два
  наших — ошибка таблицы.

## Заказы (с площадки к нам)

- Вебхуки, если площадка их даёт (inbox), иначе опрос по водяному знаку
  «изменено после − запас» каждые 5–15 минут. Каждый заказ — upsert по
  `(marketplace, order_id)`; статус меняется только вперёд по схеме статусов
  площадки (старое событие не откатывает новый статус).
- Страховка: раз в сутки — все заказы за 3 дня, сравнение статусов.
- Передача заказа в 1С (если нужна) — через outbox с ключом
  `1c:mp_order:<marketplace>:<order_id>` (см. `1c.md`).
- Подтверждение и смена статуса на площадке (принят, собран, передан) — запись
  через outbox, ключ `<marketplace>:order_status:<order_id>:<status>`.

## Остатки (от нас на площадку)

- Источник правды по остаткам — склад (1С/WMS), раздел 2 карты.
- **Доступно для площадки** = max(0, свободный остаток − резерв под открытые
  заказы всех каналов − страховой запас) ÷ `units_per_mp`, округлить вниз.
  Страховой запас — настройка клиента по SKU или категории (например, 2 шт
  или 10%): он покрывает задержку синхронизации и одновременные продажи
  на нескольких площадках.
- Если остаток делится между площадками — доля на площадку тоже настройка.
- Отправляем **только изменения** (дельта к последнему отправленному), пачками
  по лимиту площадки; раз в сутки — полная отправка всех активных SKU.
- Остаток 0 на складе — отправляем 0 сразу, вне очереди пачки (приоритет).
- Модели FBO (товар на складе площадки): остатки ведёт площадка, мы только
  читаем их для показателей.

## Цены

- Цена на площадку — из прайса клиента (1С) плюс правило канала (наценка на
  комиссию). Никогда не ниже `min_price`; изменение больше чем на X% за раз —
  в очередь на подтверждение человеку, а не сразу на площадку.
- Акции и скидки площадки — читаем, но не управляем ими в курсе.

## Сверка

- Заказы: число и сумма за день у нас = в кабинете/API площадки.
- Остатки: раз в сутки — остатки на площадке = что мы отправили последним;
  расхождение по SKU — отчёт.
- Деньги: отчёт площадки о выплате = поступление в выписке банка (`bank.md`):
  выплата приходит одной суммой за период, за вычетом комиссии — сверяем
  по отчёту площадки, а не по заказам.

## Приёмка

- [ ] тестовый заказ (или заказ на тестовом товаре) виден у нас за 15 минут;
- [ ] повторная загрузка заказов не создаёт дублей; статус не откатывается;
- [ ] остаток уменьшился на складе — на площадке уменьшился в пределах цикла;
- [ ] страховой запас и `units_per_mp` применяются; 0 уходит вне очереди;
- [ ] цена ниже `min_price` не уходит; большое изменение ждёт подтверждения;
- [ ] неизвестный SKU попадает в отчёт, а не в «пропало»;
- [ ] сверка заказов и выплат за неделю сходится.
