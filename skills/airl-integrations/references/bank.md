# Банк: выписки и платёжные поручения

Справочник `/airl-integrations`. Выписки нужны для сверки оплат, дебиторки
и платежей онлайн-оплаты; данные идут во вход модуля `bank-reconciliation`
(`src_bank_statement_lines`). Наличие API у конкретного банка и тарифа —
**уточнить в банке**: у большинства банков корпоративный API подключается
отдельным договором или только для крупных клиентов (host-to-host).

## Способы получить выписку

| Способ | Задержка | Что нужно | Комментарий |
|---|---|---|---|
| API банка | минуты–час | договор на API, сертификат/ключ, IP в белом списке | лучший вариант; есть не у всех банков и тарифов |
| Выгрузка из банк-клиента в формате 1С | сутки | бухгалтер выгружает файл или банк присылает по расписанию | есть почти везде, где работают с 1С |
| MT940 | сутки | обычно у банков с SWIFT-форматами, по запросу | стандартный формат, удобно разбирать |
| CSV/Excel из интернет-банка | сутки | ручная выгрузка | формат у каждого банка свой, меняется без предупреждения |

Ручная выгрузка — это процесс, а не интеграция: кто, во сколько, куда кладёт
файл (папка SFTP или загрузка в сервис), и оповещение, если файла за вчера нет.

## Формат 1CClientBankExchange

Текстовый файл «ключ=значение», по строке на поле; кодировка обычно Windows-1251
(указана в заголовке). Структура:

```text
1CClientBankExchange
ВерсияФормата=1.03
Кодировка=Windows
Отправитель=...           Получатель=...
ДатаСоздания=дд.мм.гггг   ВремяСоздания=чч:мм:сс
ДатаНачала=...            ДатаКонца=...
РасчСчет=<счёт>

СекцияРасчСчет
ДатаНачала=...  ДатаКонца=...  РасчСчет=...
НачальныйОстаток=...  ВсегоПоступило=...  ВсегоСписано=...  КонечныйОстаток=...
КонецРасчСчет

СекцияДокумент=Платежное поручение
Номер=...  Дата=...  Сумма=...
ПлательщикСчет=...  Плательщик=...  ПлательщикИНН=...
ПолучательСчет=...  Получатель=...  ПолучательИНН=...
ДатаСписано=...  ДатаПоступило=...
НазначениеПлатежа=...
КонецДокумента
...
КонецФайла
```

(в файле каждое поле — отдельная строка; здесь для краткости по несколько.)

- Направление: `ДатаПоступило` заполнена и наш счёт = `ПолучательСчет` — поступление;
  `ДатаСписано` и наш счёт = `ПлательщикСчет` — списание.
- Сумма — с точкой, без разделителей разрядов; проверить на файле банка.
- **Казахстан и Узбекистан**: банки и конфигурации 1С для этих стран используют
  свои варианты полей (БИН/ИИН, КБе, КНП, код назначения платежа, ИНН/СТИР, МФО) —
  набор ключей **проверить на реальном файле клиента** (обезличенном) до написания
  разбора. Неизвестные ключи разбор сохраняет в `extra`, а не падает.

## MT940

Теги: `:20:` ссылка выписки, `:25:` счёт, `:28C:` номер выписки, `:60F:`/`:60M:`
входящий остаток (D/C, дата, валюта, сумма), `:61:` строка операции (дата
валютирования, дата проводки, D/C, сумма, тип, ссылки), `:86:` описание операции
(структура подполей у банков разная — проверить), `:62F:`/`:62M:` исходящий
остаток. Десятичный разделитель — запятая.

| Банк | API выписок | Комментарий |
|---|---|---|
| Kaspi (Kaspi Business) | уточнить в банке | у малого бизнеса часто только выгрузка из приложения |
| Halyk Bank | уточнить в банке | корпоративный онлайн-банк; API/H2H — по договору |
| ForteBank, Bank CenterCredit, Jusan и др. (KZ) | уточнить в банке | |
| Kapitalbank, Hamkorbank, NBU, Ipoteka, TBC и др. (UZ) | уточнить в банке | |

Что спросить у банка: есть ли API выписок для этого тарифа; формат (JSON,
1С, MT940); как часто обновляется; есть ли песочница; аутентификация (сертификат,
OAuth, IP-список); стоимость; срок подключения. Ответы — в `INTEGRATIONS.md`.

## Загрузка и защита от дублей

- Выписки пересекаются (выгрузили «за неделю» дважды). Ключ строки: ID операции
  банка, если он есть; иначе хэш `(счёт, дата, направление, сумма, счёт контрагента,
  номер документа, назначение)` + порядковый номер одинаковых строк в выписке.
- Проверка целостности за каждый день: `входящий + поступления − списания = исходящий`;
  исходящий за день N = входящий за день N+1. Не сошлось — выписка неполная,
  оповещение, сверку по этому дню не запускаем.
- Сырые файлы хранятся (в стране, с ограниченным доступом): разбор можно повторить.

## Вход модуля `bank-reconciliation`

Модуль `airl-modules/modules/bank-reconciliation` читает представление
`src_bank_statement_lines` — его пишет эта интеграция поверх своей таблицы строк.
Колонки ровно такие (сверено с `demo_src.sql` модуля; при изменении модуля —
сверить снова):

| Колонка | Тип | Что |
|---|---|---|
| `statement_id` | text | ID выписки (файла или ответа API) |
| `bank` | text | банк |
| `account` | text | наш счёт (IBAN) |
| `line_id` | text | ключ строки (ID банка или хэш, см. выше) |
| `value_date` | date | дата операции |
| `amount` | numeric(18,2) | **со знаком**: `+` поступление, `−` списание |
| `currency` | char(3) | `KZT`, `UZS`, `USD`, ... |
| `counterparty_name` | text | контрагент |
| `counterparty_tax_id` | text | БИН/ИНН контрагента |
| `purpose` | text | назначение платежа |
| `doc_no` | text | номер платёжного документа |

В своей таблице храним больше (счёт контрагента, дата проводки, источник `api` /
`1c_file` / `mt940` / `csv`, время загрузки, сырые поля в `extra`), но в
представление отдаём только эти колонки. Второй вход модуля, `src_bank_open_items`
(счета и заявки из 1С), пишет `/airl-dwh` — не эта интеграция.

Платежи физлиц: в назначении бывают ФИО и ИИН/ПИНФЛ — модулю они не нужны;
маскировать на загрузке, если сверка работает по номеру счёта/заказа.

## Платёжные поручения — только черновики

- Интеграция создаёт **черновик** платёжки (через API банка, если умеет, или файл
  импорта в банк-клиент). Подписывает уполномоченный сотрудник клиента ЭЦП
  в банк-клиенте. Ключи подписи у нас не хранятся никогда.
- Ключ идемпотентности — ID заявки на расход из модуля согласования + версия.
  Перед созданием — поиск черновика с этим ID в назначении или поле ссылки
  (как банк позволяет — проверить).
- Сверка: черновики, созданные нами → подписанные → списания в выписке.
  Черновик старше N дней без подписи — в отчёт.
