# Онлайн-оплата: платёжные страницы, QR, подтверждение

Справочник `/airl-integrations`. В курс берётся, только если **договор
с платёжной системой (мерчант) уже подписан** (`scope.md`). Договор и подключение
мерчанта — от нескольких дней до недель (`country.md`): PM начинает на неделе 0.
Протоколы, адреса, форматы подписи — **проверить в документации платёжной системы**,
которую выдают вместе с договором; ниже — что известно и что спросить.

## Главные правила

1. **Данные карты к нам не попадают.** Покупатель вводит карту на странице
   платёжной системы (hosted page), в её приложении или по QR. Мы не храним, не
   логируем и не проксируем номер карты, CVV, срок. Своя форма ввода карты —
   никогда (это требования PCI DSS, которые нам не нужны).
2. **Оплата подтверждена только сервером платёжной системы**: вебхуком с верной
   подписью или ответом на наш запрос статуса. Возврат покупателя на «страницу
   успеха» — не подтверждение.
3. **Сумма и валюта сверяются с заказом** при каждом подтверждении. Не совпали —
   отказ и оповещение.
4. **Один заказ — один платёжный ключ.** Повторное создание платежа по тому же
   заказу возвращает существующий, а не создаёт второй.

## Платёжные системы

| Система | Страна | Что известно | Проверить |
|---|---|---|---|
| Payme (Merchant API) | UZ | Payme вызывает **наш** адрес по JSON-RPC: проверка возможности оплаты, создание, проведение, отмена транзакции, проверка статуса, выписка; авторизация вызовов — Basic с ключом мерчанта; суммы в тийинах; страница оплаты Payme Checkout | точные имена методов, коды ошибок, таймауты транзакции, поля фискализации (ИКПУ/MXIK, код упаковки) |
| Click (Click API для магазинов) | UZ | Click вызывает наш адрес в два шага: подготовка и завершение; подпись — хэш от полей запроса и секретного ключа | формат подписи (поля, порядок, алгоритм), коды ошибок, фискализация |
| Uzum (оплата/Uzum Bank) | UZ | приём оплаты через Uzum | протокол, подпись, песочница — уточнить у Uzum |
| Kaspi Pay / Kaspi QR | KZ | оплата через приложение Kaspi по QR или счёту | **уточнить в Kaspi**: есть ли API и вебхуки для вашего типа подключения; если нет — подтверждение только по выписке/отчёту Kaspi (сверка, не онлайн) |
| Halyk ePay | KZ | платёжная страница Halyk, получение токена, уведомление на наш адрес (postLink) | адрес API, формат уведомления и подписи, песочница |

Агрегаторы (несколько способов оплаты через одного провайдера) — кандидаты,
уточнить по стране в день выбора.

## Поток оплаты

```text
заказ ─► int_payments (pending) ─► ссылка на страницу оплаты / QR ─► покупатель платит
                                                                        │
          ◄── вебхук или вызов платёжной системы (подпись, сумма) ◄─────┘
int_inbox ─► payment confirmed ─► заказ оплачен ─► outbox: статус оплаты в 1С / CRM
```

- Таблица платежей (своя, в `int` или `mart_<отдел>`): `order_id`, `provider`,
  `provider_payment_id`, `amount`, `currency`, `status`
  (`pending → paid → refunded/partially_refunded`, `pending → cancelled/expired`),
  время каждого перехода. Переходы — только вперёд; повторное «paid» ничего не меняет.
- `merchant_trans_id` / `order_id`, который мы передаём платёжной системе, —
  наш ключ идемпотентности.
- В системах, где **платёжная система вызывает нас** (Payme, Click): наш адрес —
  это API с бизнес-логикой (проверить заказ, сумму, статус и ответить в формате
  протокола), а не «принял и разберу потом». Сырое тело всё равно пишем в
  `int_inbox` для аудита, ответ формируем синхронно по таблице платежей,
  с блокировкой строки заказа (`SELECT ... FOR UPDATE`).
- В системах с уведомлением (Halyk ePay и подобные) — обычный inbox: подпись →
  сохранить → 200 → разбор.
- Страховка: незавершённые платежи старше N минут — запрос статуса к API
  платёжной системы (если есть).

## Возвраты

- Только через API платёжной системы или её кабинет, никогда «перевести обратно».
- Через outbox: ключ `refund:<order_id>:<номер возврата>`; частичные возвраты —
  каждый со своим номером; сумма возвратов не больше суммы оплаты (проверка
  в нашей базе до отправки).
- Кто может инициировать возврат — роль из карты; каждый возврат в аудите.

## Фискализация

- **UZ**: для онлайн-оплаты требуются фискальные данные по позициям (коды ИКПУ/MXIK,
  единицы); Payme и Click принимают их в протоколе — проверить требования
  в документации и у бухгалтера клиента.
- **KZ**: онлайн-ККМ и ОФД — как выдаётся чек при онлайн-оплате, решает бухгалтер
  клиента; проверить, берёт ли это на себя платёжная система.

## Сверка (три стороны)

1. **Наши платежи** `paid` за день.
2. **Реестр платёжной системы** за день (выгрузка из кабинета или метод выписки).
3. **Поступления в банк** (`bank.md`): платёжная система переводит деньги пачкой
   за период за вычетом комиссии — сверяем сумму реестра минус комиссия
   с поступлением, а не каждый платёж.

Расхождения: оплачен у системы, а у нас `pending` (пропущен вебхук) — довести
статус и проверить, почему пропущен; у нас `paid`, а в реестре нет — **срочно**,
возможна подделка. Итог — в `int_reconciliation`.

## Тестирование

- Только тестовый мерчант или песочница системы и тестовые карты из документации.
- Контрактные тесты на каждый метод протокола: верная подпись, неверная подпись,
  неверная сумма, повтор, отмена после проведения, таймаут.
- Боевой запуск — с одной настоящей оплатой на минимальную сумму и возвратом,
  которые делает сотрудник клиента.

## Приёмка

- [ ] номер карты нигде у нас не появляется (поиск по логам и базе);
- [ ] неверная подпись и неверная сумма отклоняются; повтор не дублирует оплату;
- [ ] возврат на странице «успех» без вебхука не отмечает заказ оплаченным;
- [ ] полный и частичный возврат проходят, сумма возвратов ограничена;
- [ ] сверка трёх сторон за неделю сходится;
- [ ] секреты мерчанта только на сервере, отдельные для теста и боя.
