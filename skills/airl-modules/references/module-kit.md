# Как устроен модуль AIRL

Этот файл читают те, кто ставит модуль (навык `/airl-modules`) и те, кто пишет новый
модуль для библиотеки. Все модули устроены одинаково — поэтому любой участник,
поставивший один модуль, понимает остальные.

## Файлы модуля

```text
modules/<id>/
  MODULE.md      что делает, вопросы настройки, экраны, роли, показатели, приёмка
  schema.sql     таблицы, статусы, представления для экранов и показателей
  demo_src.sql   демо-источники с синтетическими данными (только для разработки)
  seed.sql       синтетические записи модуля (только для разработки)
```

## Слои

```text
источник данных (1С, CRM, свои таблицы)
        │  адаптер: представления src_<…> — пишет /airl-dwh или /airl-connect
        ▼
src_<…>        вход модуля: точный набор колонок, описанный в MODULE.md
        │
таблицы модуля  то, что вводят люди: проверки, заявки, комментарии, статусы
        │
v_<…>          представления для экранов
m_<…>          показатели модуля в едином виде (для хаба и ИИ-сводки)
```

- **Вход модуля — представления `src_<…>`** с колонками, описанными в MODULE.md.
  Модуль не знает, откуда данные: из `core` хаба, из купленной CRM, из своих таблиц
  или из выгрузки CSV. Связку пишет `/airl-dwh` (данные хранилища) или `/airl-connect`
  (данные купленной системы). Демо-версия — `demo_src.sql` с синтетикой.
- **Таблицы модуля** — только то, что вводят люди в этом модуле. Чужие данные
  не копируются, на них ссылаются по ключу источника (`client_id`, `sku`).
- **Выход** — представления `v_<…>` для экранов и `m_<…>` для показателей.

## Где лежит

- В хабе — в схеме витрины отдела `mart_<отдел>`; вход `src_<…>` там же, поверх
  `core` и `metrics`.
- В своём продукте — в схеме приложения.
- Модули одного отдела живут в одной схеме и делят каркас (`kit/kit.sql`).
- Имена таблиц модуля начинаются с его короткой приставки (`insp_`, `appr_`, `rcv_`):
  два модуля в одной схеме не конфликтуют.

Установка (пример для хаба, отдел `roastqc`):

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -c "SET search_path TO mart_roastqc" -f kit/kit.sql
```

Так `SET` действует только на первую команду. Надёжнее — один сеанс:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 <<'SQL'
SET search_path TO mart_roastqc, core, metrics;
\i kit/kit.sql
\i adapters/src_inspection_objects.sql
\i modules/inspection-journal/schema.sql
SQL
```

Порядок важен: каркас → вход `src_<…>` (адаптер, в разработке — `demo_src.sql`) →
`schema.sql` модуля, потому что представления модуля читают вход.

В проекте с миграциями каждый файл становится миграцией (одна на модуль), а
`SET search_path` — первой строкой миграции.

## Правила, общие для всех модулей

- **Ключ** — `id bigint GENERATED ALWAYS AS IDENTITY`. Бизнес-ключ (номер партии,
  номер заявки) — отдельной колонкой с `UNIQUE`.
- **Кто и когда** — `created_at`, `created_by`, `updated_at`, `updated_by` в каждой
  таблице ввода. `created_by` — идентификатор пользователя из проверенного токена
  или сессии, не из формы.
- **Статусы** — текст с `CHECK` на список значений. Каждая смена статуса пишется
  в `airl_audit` (`action = 'status'`, `from_status`, `to_status`, `comment`).
  Переходы разрешены только по схеме из MODULE.md; проверка — на сервере.
- **Деньги** — `numeric(18,2)` и валюта `char(3)` из карты или `airl-context`.
- **Время** — `timestamptz`; показывается в часовом поясе компании.
- **Удаление** — не удаляем, а ставим статус `cancelled` или флаг `archived`.
- **Файлы** — в файловом хранилище, ссылка в `airl_attachments`.
- **Персональные данные** — колонки, перечисленные в MODULE.md в разделе «Данные»,
  попадают в `pii` (`airl.service.json`) или `SPEC.md` раздел 9 и маскируются
  на сервере.
- **Уведомления** — через `airl_notifications` с уникальным `dedup_key`
  (`<модуль>:<событие>:<id>:<получатель>`): повторный запуск не шлёт дубль.
  Отмена до отправки — `cancelled_at = now()`; отправщик берёт только записи
  с `sent_at IS NULL AND cancelled_at IS NULL AND not_before <= now()`.
- **Настройки** — ответы на вопросы настройки пишутся в `airl_settings` и читаются
  функцией `airl_setting(...)`, а не зашиваются в код.
- **Имена входов** — `src_<приставка модуля>_<что>` (`src_rcv_clients`), если колонки
  нужны только этому модулю. Общее имя (`src_clients`) — только если у всех модулей,
  которые его читают, набор колонок одинаковый; иначе два модуля в одной схеме
  сломают друг другу вход.
- **Валюта компании** — одна настройка на схему: `airl_settings` с `module = 'kit'`,
  `key = 'currency'` (`"UZS"`, `"KZT"`). Модули берут её, если у модуля нет своей.
  Ставится первой при установке каркаса. Денежные пороги светофора модулей
  (просрочка, бюджет) заданы для примера — их всегда задаёт клиент в своей валюте.
- **Валюта** — денежный показатель считается в одной валюте (валюта отчётов из карты
  или `airl_settings`); записи в других валютах либо пересчитываются по курсу
  нацбанка на дату документа (если курс есть во входе), либо показываются отдельным
  списком и в итог не попадают. Складывать тенге с долларами нельзя.
- **Семейство показателей** — если показатель один, а разрезов много (выполнение
  плана по выручке, по заявкам), `metric_id` пишется как `<семейство>:<разрез>`
  (`plan_completion:revenue`). В карте (раздел 4) и в `hub.metrics` объявляется
  семейство (`plan_completion`), разрезы — его значения.
- **Показатели** — каждое представление `m_<…>` возвращает колонки
  `metric_id, period, value, unit, status`, где `status` — `ok | warning | danger`.
  В хабе `metric_id` должен быть в разделе 4 карты; если его там нет — это
  предложение в карту, а не своя формула.

## Кто читает показатели модуля

Хаб, ИИ-слой и другие читатели обращаются к `m_<…>` из своей схемы. Им нужны
`USAGE` на схему модуля, `SELECT` на нужные `m_<…>` и `SELECT` на `airl_settings`
этой схемы (пороги светофора). Таблицы модуля с вводом людей читателям не выдаются.

## Экраны

Экраны собирает `/airl-pwa` по разделу «Экраны» в MODULE.md: точные названия,
главное действие, тексты пустого состояния и ошибок. Каждый экран читает только
`v_<…>`, а пишет только в таблицы модуля через серверный API с проверкой роли.

## Как писать новый модуль

1. Модуль решает одну типовую боль, которая встречается минимум у двух разных
   компаний. Иначе это не модуль, а свой сервис.
2. Скопируй структуру любого готового модуля, раздел за разделом.
3. Вход — только через `src_<…>` с перечисленными колонками.
4. Проверь на чистой базе PostgreSQL 16: `kit.sql`, `schema.sql`, `demo_src.sql`,
   `seed.sql` выполняются без ошибок, каждое `v_` и `m_` возвращает строки.
   Скрипт: `scripts/test_modules.sh`.
5. Добавь строку в каталог (`references/catalog.md`).
