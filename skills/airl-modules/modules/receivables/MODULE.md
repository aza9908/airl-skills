# Дебиторка (`receivables`)

**Боль.** Кто сколько должен и с какого дня — знает только бухгалтер, и только после
выгрузки из 1С. Менеджер отгружает клиенту сверх лимита, обещания «заплатим в пятницу»
живут в голове, а руководитель узнаёт о долге старше трёх месяцев, когда клиент уже
закрылся.

**Кто пользуется.** Менеджер (свои клиенты: долг, звонки, обещания), бухгалтер или
финансист по дебиторке (все клиенты, претензии, качество данных), руководитель
(просрочка по менеджерам и динамика).

**Приставка таблиц:** `rcv_`

## Что закрывает

- возраст долга по клиенту: не просрочено, 1–30, 31–60, 61–90, больше 90 дней;
- просрочка по клиентам и менеджерам, использование кредитного лимита;
- журнал действий по взысканию и обещания оплатить с автоматической проверкой
  «выполнено / нарушено»;
- список документов без срока оплаты и других ошибок данных — отдельно, а не молча
  «в срок»;
- маркетплейсы и агрегаторы — отдельной строкой, не портят показатели клиентов.

Пример соответствия: в ТЗ STEP COFFEE это FIN-008, BI-005, CRM-002 (кредитный лимит
и отсрочка), часть AI Finance («дебиторка»); в частной клинике в Самарканде — долги
страховых компаний и корпоративных клиентов по договорам ДМС.

## Настройка — вопросы

Задавай по одному, с вариантами и рекомендацией. Ответы — в `airl_settings`
(`module = 'receivables'`).

| № | Вопрос | Ключ | По умолчанию |
|---|---|---|---|
| 1 | Основная валюта (в ней показатели) | `currency` | валюта отчётов из карты (KZT, UZS, …) |
| 2 | Если в документе нет срока оплаты — брать отсрочку из договора клиента? | `use_contract_terms` | да |
| 3 | Кто у вас агрегаторы (Kaspi, Halyk Market, Uzum Market, Wildberries…) и считать ли их в показателях | `is_aggregator` в адаптере, `include_aggregators` | не считать |
| 4 | Пороги просрочки в деньгах: жёлтый, красный | `overdue_warn`, `overdue_bad` | 3 млн и 10 млн |
| 5 | Пороги доли просрочки, % | `share_warn`, `share_bad` | 20% и 35% |
| 6 | Насколько можно недоплатить, чтобы обещание считалось выполненным, % | `promise_tolerance_pct` | 5 |
| 7 | Кому сообщать о превышении лимита и долгах 90+ | `finance_recipient` | `role:fin_director` |
| 8 | Куда слать уведомления | `channel` | telegram |

## Данные

**Вход** — представления, которые пишет `/airl-dwh` (1С: реализации и оплаты) или `/airl-connect`:

| Представление | Колонка | Тип | Что |
|---|---|---|---|
| `src_receivables_docs` | `client_id` | text | код клиента |
| | `client_name` | text | название |
| | `doc_no` | text | номер реализации; возврат — отдельный документ с минусом |
| | `doc_date` | date | дата документа |
| | `due_date` | date | срок оплаты; NULL — не указан |
| | `amount`, `paid_amount` | numeric | сумма и сколько уже оплачено |
| | `currency` | char(3) | валюта |
| | `manager_id`, `branch_id` | text | менеджер, филиал |
| `src_rcv_clients` | `client_id`, `client_name` | text | клиент |
| | `credit_limit` | numeric | кредитный лимит; NULL — не задан |
| | `payment_terms_days` | int | отсрочка по договору, дней |
| | `manager_id` | text | закреплённый менеджер |
| | `is_aggregator` | boolean | маркетплейс или агрегатор |

**Таблицы модуля:** `rcv_actions` (звонки, письма, встречи, претензии, остановка
отгрузок), `rcv_promises` (обещания оплатить: дата, сумма).

**Статусы.** Действие: `active → archived`. Обещание: `active → cancelled` (с комментарием);
итог считается сам в `v_rcv_promises`:

```text
waiting ──(оплатили ≥ суммы − допуск)──► kept
   └─────(дата прошла, не оплатили)────► broken
```

«Оплачено после обещания» = долг по документам на дату обещания минус долг по тем же
документам сейчас.

**Персональные данные:** нет, если клиенты — юрлица. Если среди клиентов ИП или
физлица — их имена в `client_name` попадают в `pii`.

## Экраны

1. **«Должники»** (`v_rcv_aging`) — главный экран: клиент, всего долг, корзины
   возраста, лимит и % использования, последнее действие, обещание. Сортировка —
   по просрочке. Главная кнопка: **«Записать звонок»**; в форме — **«Клиент обещал
   оплатить»** (дата и сумма обязательны). Менеджер видит только своих — фильтр
   на сервере по `manager_id`. Пусто: «Просроченных долгов нет».
2. **«Клиент»** — документы клиента (`v_rcv_docs`), действия (`v_rcv_actions`),
   обещания (`v_rcv_promises`).
3. **«По менеджерам»** (`v_rcv_by_manager`) — для руководителя; агрегаторы отдельной
   строкой.
4. **«Качество данных»** (`v_rcv_data_quality`) — нет срока оплаты, нет клиента
   в справочнике, переплата, другая валюта, нет лимита. Пусто: «Ошибок в данных нет».

Ошибка сети при сохранении звонка: «Звонок не сохранён. Текст остался в форме —
нажмите «Сохранить» ещё раз».

## Роли

| Действие | Менеджер | Финансист | Руководитель |
|---|---|---|---|
| видеть долги | своих клиентов | всех | всех |
| записать звонок, обещание | да | да | нет |
| претензия, остановка отгрузок | нет | да | да |
| отменить обещание | своё | да | нет |
| «Качество данных» | свои клиенты | да | да |

## Показатели

| id | Формула | Светофор |
|---|---|---|
| `receivables_overdue` | сумма остатков документов с прошедшим сроком оплаты на сегодня (срок — из документа или по отсрочке), основная валюта, без агрегаторов; единица — валюта из `currency` | `overdue_warn`, `overdue_bad` (меньше — лучше) |
| `receivables_overdue_share` | просрочка / весь открытый долг × 100 на сегодня, те же фильтры | `share_warn`, `share_bad` (меньше — лучше) |

Документы без срока оплаты в просрочку **не входят** — они в «Качестве данных».
В хабе оба `id` должны быть в разделе 4 карты.

## Что уходит в хаб

`receivables_overdue`, `receivables_overdue_share`; предупреждение — число нарушенных
обещаний и клиентов сверх лимита.

## Уведомления

Функция `rcv_queue_notifications()` (раз в день, утром):
- обещание нарушено — менеджеру клиента, один раз на обещание;
- клиент сверх лимита — менеджеру и `finance_recipient`, раз в месяц на клиента;
- документ перешёл в 90+ — `finance_recipient`, один раз на документ.

## Приёмка

- [ ] сумма долга по 5 клиентам совпадает с актом сверки из 1С на ту же дату;
- [ ] документ без срока оплаты и без отсрочки клиента виден в «Качестве данных»,
      а не в «не просрочено»;
- [ ] маркетплейсы-агрегаторы не входят в `receivables_overdue`;
- [ ] менеджер не видит чужих клиентов (проверено запросом под его ролью);
- [ ] обещание без даты или суммы не сохраняется;
- [ ] после оплаты в 1С обещание переходит в «выполнено» со следующей загрузкой.

## После курса

Автоматическая остановка отгрузок сверх лимита в заказе (CRM), акт сверки в PDF,
прогноз поступлений по обещаниям и срокам.

## Ловушки

- Частичная оплата: остаток документа — `amount − paid_amount`; в источнике оплата
  должна быть разнесена по документам, иначе старые долги «висят» при оплаченных новых.
- Возвраты и корректировки (кредит-ноты) приходят отдельным документом с минусом.
  В просрочку они не засчитываются (не привязаны к счёту), а уменьшают долг для лимита.
  Если 1С привязывает возврат к реализации — лучше уменьшать `paid_amount` в адаптере.
- Агрегатор (Kaspi) — это расчёты по графику выплат маркетплейса, а не долг клиента.
- Продажи внутри группы (ТОО Алматы ↔ ТОО Астана) — исключай в адаптере, иначе
  просрочка «своих» пугает руководителя.
- Отсрочка в банковских днях против календарных: уточни, как считает бухгалтерия.
- Обещание на всю сумму, а клиент тем временем получил новую отгрузку — модуль
  смотрит только документы на дату обещания, новая отгрузка не мешает.
