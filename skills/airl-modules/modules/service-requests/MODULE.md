# Сервисные заявки (`service-requests`)

**Боль.** Заявки на ремонт приходят звонком, в Telegram и через менеджера, и живут
в переписке. Не видно, кто из техников чем занят, какая заявка горит, какие
запчасти поставили и списали ли их. Одна и та же машина ломается каждый месяц —
и никто этого не замечает. Плановое обслуживание вспоминают после поломки.

**Кто пользуется.** Диспетчер (принимает и назначает), техник (выполняет, пишет
акт), руководитель сервиса (сроки, повторные поломки, загрузка), клиент — только
подтверждает акт.

**Приставка таблиц:** `svc_`

## Что закрывает

Типовые требования, которые закрываются настройкой этого модуля:

- электронная заявка на ремонт, обслуживание, установку или выезд специалиста;
- паспорт оборудования: модель, серийный номер, клиент, адрес, гарантия, история;
- назначение техника, приоритет и срок по SLA;
- статусы ремонта и уведомления о просрочке;
- учёт запчастей по заявке (списание в учёте делает человек — модуль помнит номер документа);
- сервисный акт с фото и подтверждением клиента;
- плановое обслуживание: заявки создаются сами по графику;
- повторные поломки и загрузка техников.

Пример соответствия: в ТЗ STEP COFFEE это SERVICE-001…008, SERVICE-009 (выезд
бариста — вид заявки `barista_service`), процесс BP-009. В клинике — заявки на
ремонт и плановое обслуживание медицинского оборудования (вид `medical_device`):
УЗИ-аппарат, автоклав, стоматологические установки.

## Настройка — вопросы

Задавай по одному, с вариантами и рекомендацией. Ответы — в `airl_settings`
(`module = 'service-requests'`).

| № | Вопрос | Ключ | По умолчанию |
|---|---|---|---|
| 1 | Откуда список клиентов: CRM · 1С · ведём сами | — (адаптер `src_clients`) | из CRM |
| 2 | Есть ли справочник запчастей в учёте | — (адаптер `src_parts`, может быть пустым) | из 1С |
| 3 | За сколько часов закрываем заявку по приоритету: критичный · высокий · обычный · низкий | `sla_hours` | 8 · 24 · 72 · 168 |
| 4 | Через сколько дней после ремонта новая поломка считается повторной | `repeat_days` | 30 |
| 5 | Какое оборудование обслуживаем по графику и как часто | таблица `svc_maint_plans` | по договорам клиентов |
| 6 | За сколько дней создавать плановую заявку | `plan_horizon_days` | 14 |
| 7 | Кому сообщать о просрочке | `escalate_to` | руководитель сервиса |
| 8 | Как клиент подтверждает акт: код в сообщении · подпись на экране · бумага | — (поле `confirm_method`) | код |
| 9 | Пороги светофора: просрочка SLA и повторные поломки | `sla_breach_warn`, `sla_breach_bad`, `repeat_warn`, `repeat_bad` | 10% и 20%; 5% и 10% |

Список оборудования переноси **из реальной таблицы или договоров клиента**
(серийные номера — с шильдиков), не придумывай.

## Данные

**Вход** — представления, которые пишет `/airl-dwh` или `/airl-connect`:

| Представление | Колонки |
|---|---|
| `src_clients` | `client_id` text, `client_name` text, `city` text, `address` text, `phone` text (может быть пусто) |
| `src_parts` | `sku` text, `part_name` text, `unit` text |

`src_clients` — общий вход с модулем `complaints`: колонки одинаковые, адаптер
пишется один раз. Нет справочника запчастей — адаптер
`CREATE VIEW src_parts AS SELECT NULL::text AS sku, NULL::text AS part_name, NULL::text AS unit WHERE false`.

**Таблицы модуля:** `svc_equipment` (паспорт), `svc_requests` (заявки),
`svc_parts_used` (запчасти), `svc_acts` (акты), `svc_maint_plans` (график ТО).
Фото к акту — в `airl_attachments` (`entity = 'svc_acts'`).

**Статусы заявки** (`svc_requests.status`):

```text
new ──► assigned ──► in_progress ──► done ──► closed (только с подтверждённым актом)
 │          │          │   ▲   ▲       │
 │          │          ▼   │   └───────┘ (клиент не принял — снова в работу)
 │          │       waiting_parts
 └──────────┴──────────┴───► cancelled (причина обязательна)
```

Переходы проверяет база (триггер), каждая смена — строка в `airl_audit`. Срок
`due_at` ставится сам при создании: от времени заявки (или плановой даты) + часы
по приоритету.

**Персональные данные:** телефон клиента (`src_clients.phone`) и имя принявшего
работу (`svc_acts.signer_name`) — в `pii`, маска для всех, кроме диспетчера
и руководителя сервиса. Код подтверждения хранится только хешем.

## Экраны

1. **«Заявки»** — главный экран диспетчера: открытые заявки, просроченные сверху
   красным, повторные с меткой «повтор». Главная кнопка: **«Новая заявка»**.
   Пусто: «Открытых заявок нет. Новые появятся здесь сразу после создания».
2. **«Мои заявки»** (техник, с телефона) — назначенные ему, по сроку. Кнопки по
   статусу: **«Начать»** · **«Жду запчасть»** · **«Готово»** (обязательно: что
   сделано, запчасти, фото). Пусто: «На вас нет заявок».
3. **«Акт»** — что сделано, запчасти, фото, кнопка **«Отправить код клиенту»**
   и поле кода. Неверный код: «Код не подошёл. Проверьте последнее сообщение
   или отправьте код ещё раз».
4. **«Оборудование»** — паспорт: гарантия, последнее ТО, следующее ТО, история
   ремонтов, число повторных поломок.

Ошибка сети: «Не удалось сохранить заявку. Данные остались в форме — нажмите
«Сохранить» ещё раз».

## Роли

| Действие | Диспетчер | Техник | Руководитель сервиса | Руководитель |
|---|---|---|---|---|
| видеть все заявки | да | только свои | да | да |
| создать заявку, назначить техника | да | нет | да | нет |
| менять статус «в работе / жду / готово» | нет | свои | да | нет |
| закрыть, отменить | да | нет | да | нет |
| паспорт оборудования и график ТО | да | смотреть | да | смотреть |

## Показатели

| id | Формула | Светофор |
|---|---|---|
| `service_sla_breach_rate` | заявки, выполненные позже `due_at` / все выполненные (статус `done` или `closed`) за месяц, по дате выполнения `done_at` | `sla_breach_warn`, `sla_breach_bad` (меньше — лучше) |
| `repeat_breakdown_rate` | ремонты, начатые не позже `repeat_days` после предыдущего завершённого ремонта той же единицы / все ремонты (кроме отменённых) за месяц, по дате создания заявки | `repeat_warn`, `repeat_bad` (меньше — лучше) |

В хабе оба `id` должны быть в разделе 4 карты.

## Что уходит в хаб

`service_sla_breach_rate`, `repeat_breakdown_rate`; предупреждение — число
открытых просроченных заявок и запчастей без номера списания.

## Уведомления

- новая заявка с приоритетом «критичный» — руководителю сервиса, сразу;
- назначение — технику, сразу (`service-requests:assigned:<id>:<техник>`);
- просрочка SLA — технику и `escalate_to`, один раз на заявку (функция `svc_notify_overdue()`, запускать каждые 15 минут);
- смена статуса — клиенту, если он дал согласие на сообщения (текст без цен и диагнозов).

## Приёмка

- [ ] заявка, созданная в 10:00 с приоритетом «высокий», получает срок 10:00 следующего дня;
- [ ] перевод `new → done` минуя «в работе» база отклоняет;
- [ ] заявку нельзя закрыть без подтверждённого акта;
- [ ] вторая поломка той же машины через 10 дней помечена «повтор»;
- [ ] `svc_generate_planned()` дважды подряд не создаёт дублей плановых заявок;
- [ ] техник не видит чужие заявки (проверено запросом под его ролью).

## После курса

Автоматическое списание запчастей в 1С по API, выручка и затраты по заявке
из учёта (SERVICE-008 полностью), маршрут техника на карте, портал клиента.

## Ловушки

- Одна машина — разные клиенты со временем (переезд, продажа): история остаётся
  у оборудования, `client_id` в заявке — на момент заявки.
- Плановое ТО не считается поломкой и не входит в `repeat_breakdown_rate`.
- «Жду запчасть» не останавливает срок SLA — если это нечестно для клиента,
  договоритесь о сроке заранее и меняйте приоритет, а не статус.
- Запчасть «поставили», но не списали в учёте — смотри `v_svc_parts`, колонку `awaiting_write_off`.
