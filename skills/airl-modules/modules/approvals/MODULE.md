# Согласование заявок (`approvals`)

**Боль.** Заявки на оплату и закупку согласуют в мессенджере: фото счёта, «ок» от
руководителя, потом финдиректор переспрашивает. Никто не видит, у кого заявка
застряла, сколько осталось бюджета статьи и почему оплатили сверх лимита. Через месяц
не восстановить, кто и когда разрешил платёж.

**Кто пользуется.** Сотрудник (создаёт заявку), согласующие по маршруту — руководитель
подразделения, закупки, финансовый директор, первый руководитель; бухгалтер (отмечает
оплату); финансы (ведут бюджеты и правила маршрутов).

**Приставка таблиц:** `appr_`

## Что закрывает

- заявки на оплату поставщикам, сотрудникам и подрядчикам, на расход, на закупку
  и на внеплановую закупку — с номером счёта или договора и файлом во вложении;
- маршрут согласования по сумме, подразделению и виду расхода — таблицей правил,
  без программиста;
- бюджет подразделение × статья × месяц и остаток бюджета на момент решения;
- отметки нестандартных операций: сверх бюджета, нет бюджета, нет документа, новый
  контрагент, крупная сумма;
- история: кто, когда, какое решение и с каким комментарием.

Пример соответствия: в ТЗ STEP COFFEE это FIN-001, FIN-002, FIN-003, FIN-004 (ссылка
на счёт/договор), FIN-009, FIN-010, PURCHASE-007, WORK-003 и процесс BP-006;
в частной клинике в Ташкенте — заявки на закупку расходников и ремонт оборудования
с согласованием главврачом и финансистом, бюджет по отделениям.

## Настройка — вопросы

Задавай по одному, с вариантами и рекомендацией. Ответы — в `airl_settings`
(`module = 'approvals'`) и в таблицах правил.

| № | Вопрос | Ключ | По умолчанию |
|---|---|---|---|
| 1 | Какие виды заявок нужны: оплата · расход · закупка · внеплановая закупка | `request_type` (список в схеме) | все четыре |
| 2 | Какие статьи расходов; по каким есть бюджет; где обязателен счёт | `appr_categories` | по плану счетов клиента |
| 3 | Кто согласует при какой сумме, подразделении, статье — по шагам | `appr_rules`, `appr_rule_steps` | до 100 тыс — руководитель; до 1 млн — + финдиректор; от 1 млн — + первый руководитель |
| 4 | Валюта учёта (в ней бюджеты и пороги) | `currency` | валюта отчётов из карты (KZT, UZS, …) |
| 5 | С какой суммы операция «крупная» | `large_amount` | 5 000 000 |
| 6 | Сколько дней контрагент считается «новым» | `new_counterparty_days` | 90 |
| 7 | Через сколько часов напомнить согласующему | `remind_hours` | 24 |
| 8 | Пороги светофора для срока согласования, часов | `cycle_warn_hours`, `cycle_bad_hours` | 24 и 72 |
| 9 | Куда слать уведомления: telegram · email · in_app | `channel` | telegram |

Правила маршрута составляй **по реальному регламенту**: попроси приказ о лимитах
подписи или таблицу «кто что подписывает». Не придумывай пороги сам.

## Данные

**Вход** — представления, которые пишет `/airl-dwh` или `/airl-connect`:

| Представление | Колонка | Тип | Что |
|---|---|---|---|
| `src_appr_departments` | `dept_id` | text | код подразделения |
| | `dept_name` | text | название |
| | `branch_id` | text | филиал |
| | `head_user_id` | text | руководитель (для шага `dept_head`) |
| `src_appr_counterparties` | `counterparty_id` | text | код контрагента в 1С |
| | `counterparty_name` | text | название |
| | `counterparty_type` | text | supplier · contractor · employee |
| | `tax_id` | text | БИН/ИИН |
| | `first_deal_date` | date | первая сделка (для «новый контрагент») |

**Таблицы модуля:** `appr_categories`, `appr_rules`, `appr_rule_steps`, `appr_budgets`,
`appr_requests`, `appr_steps`. Сумма заявки — `amount` + `currency`, в валюте учёта —
`amount_base` (по курсу на дату заявки); бюджет и маршрут считаются по `amount_base`.

**Статусы заявки** (`appr_requests.status`):

```text
draft ──► on_approval ──► approved ──► paid
  │            ├────────► rejected
  │            ├────────► returned ──► on_approval (новый круг)
  ▼            ▼              ▼
cancelled   cancelled     cancelled
```

Переходы проверяет триггер в базе; каждая смена — строка в `airl_audit`. Отправку
и решения делают функции `appr_submit(...)` и `appr_decide(...)`: они создают шаги
по правилу, ведут очередь и не дают автору согласовать свою заявку. Роль
согласующего проверяет сервер перед вызовом.

**Персональные данные:** ИИН и ФИО сотрудников-получателей (контрагенты типа
`employee`) — в `pii`, маскировать на сервере.

## Экраны

1. **«Мне на согласование»** (`v_appr_inbox`) — главный экран согласующего: сумма,
   назначение, остаток бюджета, отметки отклонений, сколько часов ждёт. Кнопки:
   **«Согласовать»** · **«Вернуть на доработку»** · **«Отклонить»** (для двух последних
   обязателен комментарий). Пусто: «Нет заявок, которые ждут вашего решения».
2. **«Мои заявки»** (`v_appr_requests`) — главная кнопка **«Новая заявка»**; в черновике
   видно, кто будет согласовывать (`v_appr_route`). Пусто: «Вы ещё не создавали заявок.
   Нажмите «Новая заявка»».
3. **«Бюджеты»** (`v_appr_budget`) — подразделение × статья: бюджет, на согласовании,
   одобрено, оплачено, остаток. Красным — перерасход.
4. **«Отклонения»** (`v_appr_deviations`) — для финансов: заявки с отметками.
   Пусто: «Нестандартных операций нет».

Ошибка сети при решении: «Решение не сохранено. Проверьте связь и нажмите кнопку ещё раз».
Нет правила: «Для этой заявки не настроен маршрут. Обратитесь в финансовый отдел».

## Роли

| Действие | Сотрудник | Согласующий | Бухгалтер | Финансы |
|---|---|---|---|---|
| создать и отправить заявку | да | да | да | да |
| решение по шагу своей роли | нет | да | нет | нет |
| отметить «оплачено» | нет | нет | да | нет |
| бюджеты и правила маршрута | нет | нет | нет | да |
| видеть все заявки | только свои | свои и на согласовании | одобренные | да |

## Показатели

| id | Формула | Светофор |
|---|---|---|
| `approval_cycle_hours` | медиана часов от первой отправки (`submitted_at`) до итогового решения (`decided_at`), по месяцу решения | `cycle_warn_hours`, `cycle_bad_hours` (меньше — лучше) |
| `budget_overrun_count` | строки бюджета месяца, где одобрено + оплачено больше бюджета, по месяцу бюджета | 0 — зелёный, 1–2 — жёлтый, 3 и больше — красный |

В хабе оба `id` должны быть в разделе 4 карты.

## Что уходит в хаб

`approval_cycle_hours`, `budget_overrun_count`; предупреждение — число заявок, которые
ждут решения дольше `remind_hours`.

## Уведомления

Функция `appr_queue_notifications()` (запускать по расписанию, раз в 15–30 минут):
- новый шаг — согласующему (пользователю или `role:<роль>`), один раз на шаг;
- шаг ждёт дольше `remind_hours` — напоминание, один раз;
- согласовано, отклонено, возвращено — автору заявки.

## Приёмка

- [ ] правила маршрута совпадают с приказом о лимитах (проверил финдиректор на 5 реальных заявках);
- [ ] заявка без правила не отправляется и показывает текст ошибки;
- [ ] «Вернуть» и «Отклонить» без комментария не сохраняются;
- [ ] автор не может согласовать свою заявку (проверено запросом под его ролью);
- [ ] переход «отклонена → оплачена» отбивается базой;
- [ ] остаток бюджета на экране совпадает с ручным расчётом финансов за прошлый месяц;
- [ ] заявка сверх бюджета и без счёта видна в «Отклонениях».

## После курса

Импорт банковской выписки и сверка «оплачено» с платёжкой (FIN-005), выгрузка
одобренных заявок в 1С (FIN-006), замещение согласующего на время отпуска.

## Ловушки

- **Без приказа руководителя модуль будет пустым.** Согласование меняет работу
  20–40 человек вне курса: нужен приказ «оплата только по заявке в системе с даты …»
  до недели 3. Иначе заявки по-прежнему идут в мессенджере.

- Заявка в валюте (зерно в USD): бюджет считается по `amount_base`. Курс фиксируй
  на дату заявки, а не оплаты — иначе остаток бюджета «плывёт».
- Правило поменяли, пока заявка в пути: правило фиксируется при отправке (`rule_id`),
  новые пороги действуют только для новых отправок.
- Возврат на доработку начинает новый круг со всеми шагами заново; срок согласования
  считается от **первой** отправки — честно для заявителя.
- Одна закупка дробится на несколько заявок «до 100 тысяч», чтобы обойти маршрут.
  Смотри в «Отклонениях» несколько заявок одному контрагенту за день.
- Руководитель подразделения сам создаёт заявку — шаг `dept_head` он пройти не может;
  договорись, кто его замещает (обычно следующий по маршруту).
- Подотчётные суммы сотрудникам — это тоже контрагенты; ИИН — персональные данные.
