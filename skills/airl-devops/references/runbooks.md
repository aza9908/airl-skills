# Что делать, если… (ранбуки)

Короткие инструкции на случай сбоя. Каждая: признаки → первые 5 минут (только
смотреть) → что делать → когда остановиться и звать человека → что записать.

Общие правила:

- **Первые 5 минут — только команды из зелёной зоны памятки** (`docker ps`, `df -h`,
  `docker logs`). Ничего не удалять и не перезапускать, пока не понятно, что случилось.
- Перед любым действием из жёлтой и красной зоны — **снимок диска в панели провайдера**,
  если он есть, и свежая копия базы, если база отвечает.
- Записывай по ходу: время, что видел, что сделал. Это понадобится специалисту и для
  журнала инцидентов.
- Контакт эскалации — в `DEVOPS.md` (вопрос 8). Звони, не стесняясь: 10 минут
  специалиста дешевле, чем потерянная база.

Подставь значения: `<проект>-prod` — папка среды, `app` — имя службы (в хабе — `id`
сервиса), `<порт>` — `APP_PORT` из `.env`.

## 1. Сервис не отвечает

**Признаки:** оповещение Uptime Kuma, `https://<домен>` не открывается или отдаёт 502/504.

**Первые 5 минут:**

```bash
ssh <пользователь>@<IP>
```

Нет входа по SSH вообще — сразу к пункту «Звать человека» и в консоль восстановления
в панели провайдера.

```bash
cd /srv/<проект>-prod && docker compose ps
```

```bash
curl -fsS http://127.0.0.1:<порт>/healthz
```

```bash
docker compose logs --tail 100 app
```

```bash
df -h / && free -h
```

```bash
cd /srv/proxy && docker compose ps && docker compose logs --tail 50 caddy
```

**Что делать — по тому, что увидел:**

| Увидел | Действие |
|---|---|
| Контейнер `app` остановлен (`Exited`) | `cd /srv/<проект>-prod && docker compose up -d app`, затем снова `/healthz` |
| `app` перезапускается по кругу, в логах ошибка после недавней выкладки | раздел 4 — откат |
| В логах «connection refused» к базе | раздел 3 — база |
| Диск 100% | раздел 2 |
| `/healthz` на `127.0.0.1` отвечает, а снаружи нет | прокси: `cd /srv/proxy && docker compose up -d`; проверить DNS `nslookup <домен>`; не правили ли Caddyfile |
| Память на нуле, в `dmesg -T \| tail` есть `Out of memory` | `docker stats --no-stream` — кто съел; перезапустить этот контейнер; добавить лимит `mem_limit` и разобраться днём |
| Всё зелёное на сервере, снаружи не открывается | сеть провайдера или атака: панель провайдера, страница статуса провайдера |

**Звать человека:** нет входа по SSH; после перезапуска падает снова, а причина в логах
непонятна; подозрение на взлом (чужие процессы в `top`, незнакомые входы в `last`).

**Записать:** время начала и конца, причина, что сделали, что поменять, чтобы не повторилось.

## 2. Диск заполнен

**Признаки:** оповещение «диск больше 80%», ошибки `No space left on device`, база
перестала принимать запись.

**Первые 5 минут:**

```bash
df -h
```

```bash
sudo du -xh --max-depth=2 / 2>/dev/null | sort -h | tail -n 20
```

```bash
docker system df
```

```bash
ls -lh /srv/<проект>-prod/backups | tail -n 20
```

**Что делать — от безопасного к осторожному:**

1. Старые неиспользуемые образы (тома и данные не трогает; жёлтая зона, но безопасно):

```bash
docker image prune -a --filter "until=168h"
```

2. Системный журнал:

```bash
sudo journalctl --vacuum-size=500M
```

3. Логи контейнеров без ограничения (если `daemon.json` не настроен): найти большие
   файлы `sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail`
   и очистить конкретный файл, не удаляя: `sudo truncate -s 0 <путь к файлу>`.
   Затем настроить ограничение (часть 6 `server-setup.md`).
4. Старые локальные копии базы — **только если есть свежая копия вне сервера**
   и она проверена: удалить самые старые файлы `db_*.dump` по одному, а не маской.
5. Не помогло — увеличить диск в панели провайдера (обычно без остановки, но
   расширение раздела после — с человеком, который делал это раньше).

**Никогда:** `docker system prune --volumes`, `docker volume prune`, удаление файлов
из `/var/lib/docker/volumes` или `/var/lib/postgresql` — это данные базы.

**Звать человека:** диск 100% и база не запускается; непонятно, что занимает место;
нужно расширять раздел.

**Записать:** что заняло место; поставить оповещение на 80% (`server-checks.sh`),
если его не было.

## 3. База не запускается

**Признаки:** контейнер `db` в статусе `Restarting` или `Exited`, приложение пишет
«connection refused».

**Первые 5 минут:**

```bash
cd /srv/<проект>-prod && docker compose ps db && docker compose logs --tail 100 db
```

```bash
df -h
```

```bash
docker volume ls | grep <проект>
```

**Что делать — по тексту в логах:**

| В логах | Причина | Действие |
|---|---|---|
| `No space left on device` | диск | раздел 2, затем `docker compose up -d db` |
| `database files are incompatible with server` | сменилась основная версия образа (`postgres:16` → `17`) | вернуть прежнюю версию образа в `docker-compose.yml`, `docker compose up -d db`. Обновление версии — отдельная работа с `pg_upgrade` или выгрузкой, со специалистом |
| `could not open file` / `invalid page` / `PANIC` | повреждение данных | **стоп**: ничего не перезапускать по кругу, снимок диска, звать человека |
| `password authentication failed` (у приложения) | поменяли пароль в одном файле, а не в обоих | сверить `.env.app` и `.env.db` (значения не печатать) |
| `FATAL: the database system is in recovery mode` | база восстанавливается после сбоя | подождать 5–10 минут и смотреть логи; не перезапускать |
| `archive command failed` (PITR) | хранилище журнала недоступно | база работает, но журнал копится на диске: проверить ключи и доступ к хранилищу, следить за диском |

Порядок проверки, что том на месте: в `docker volume ls` есть том вида
`<проект>-prod_db_data`. **Нет тома — не запускать базу «с нуля»**: она создастся
пустой поверх. Звать человека.

**Звать человека:** повреждение данных, нет тома, ошибка непонятна, база не поднялась
за 15 минут. Решение «восстановить из копии» — раздел 6, и тоже не в одиночку, если
восстановление ни разу не проверяли.

## 4. Плохая выкладка → откат

**Признаки:** после выкладки ошибки у пользователей, оповещение, красная задача
в GitHub Actions.

`deploy.sh` откатывается сам, если новая версия не ответила на `/healthz`. Этот раздел —
когда `/healthz` зелёный, но продукт работает неправильно.

**Первые 5 минут:**

```bash
cd /srv/<проект>-prod && tail -n 5 deploy.log && cat .previous_tag
```

```bash
docker compose logs --since 15m app | grep -i error | tail -n 30
```

**Откат кода** (зелёная/жёлтая зона: база не меняется):

```bash
/srv/<проект>-prod/deploy.sh "$(cat /srv/<проект>-prod/.previous_tag)"
```

или в GitHub: **Actions → ci-cd → Run workflow**, `image_tag` = хеш из `.previous_tag`.

Проверить: `/healthz` отдаёт прежнюю `version`, главное действие работает.

**Если вместе с версией была миграция:** по правилу expand/contract старый код работает
с расширенной базой — откат кода безопасен. Миграции «вниз» не запускаем. Если миграция
была «contract» (удаляла колонку или таблицу) и данные пропали — это раздел 6, со
специалистом.

**После:** исправление — новой версией через staging, не правкой на сервере.
Запиши в `DEVOPS.md`: что сломалось, почему проверки и staging этого не поймали,
какой тест добавить.

**Звать человека:** откат не помог; ошибка в данных, а не в коде.

## 5. Утёк ключ или пароль

**Признаки:** ключ попал в git, в чат, на скриншот; письмо от GitHub или сервиса
о найденном секрете; неожиданные списания у платного API; незнакомые входы.

**Сразу, в этом порядке:**

1. **Отозвать или заменить секрет в кабинете сервиса** — это главное. Удаление строки
   из кода не помогает: ключ уже скопирован. Порядок замены — `operations.md`,
   «Ротация секретов»; при утечке сначала **отзываем**, даже ценой короткой остановки
   интеграции.
2. Вписать новое значение на сервере (`.env.app`, права `600`) и в секреты GitHub,
   перезапустить приложение: `docker compose up -d --no-deps app`, проверить `/healthz`.
3. Посмотреть журнал использования в кабинете сервиса: были ли вызовы, которых вы
   не делали, и с каких адресов. Деньги — поставить потолок расходов.
4. Если утёк ключ SSH или доступ к серверу:

```bash
last -n 30
```

```bash
sudo grep -E 'Accepted|Failed' /var/log/auth.log | tail -n 50
```

   удалить ключ из `~/.ssh/authorized_keys`, сменить ключи выкладки, проверить
   `crontab -l` и `docker ps` на чужое.
5. Если утёк пароль базы — сменить (`operations.md`), проверить, что порт базы закрыт
   снаружи (`nc -zv <IP> 5432` с компьютера — отказ).
6. Убрать секрет из кода и истории: заменить на переменную окружения; переписывать
   историю git — только со специалистом и после замены ключа.

**Звать человека:** признаки, что ключом уже воспользовались; доступ к серверу или
базе с чужих адресов; утекли персональные данные — это ещё и вопрос закона
(уведомление по разделу «Страна и закон» в `ARCHITECTURE.md`), сообщить руководителю
и юристу.

**Записать:** что утекло, когда заметили, когда заменили, были ли чужие действия.

## 6. Восстановление из копии

**Когда:** данные потеряны или испорчены (ошибочное удаление, сбой миграции, повреждение
базы). **Это красная зона**: рабочая база будет заменена.

**До начала:**

1. Остановить запись, чтобы не было новых данных поверх: `docker compose stop app`
   (продукт недоступен — предупредить людей).
2. Сохранить то, что есть сейчас, даже если оно испорчено:

```bash
cd /srv/<проект>-prod && docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > backups/before_restore_$(date +%F_%H%M).dump
```

3. Решить, на какой момент восстанавливать, и **сначала восстановить во временную
   базу** и проверить там (часть 5 `server-setup.md`, «Проверка восстановления»).

### Из ежедневной копии `pg_dump`

После проверки во временной базе — в рабочую (с «да» и, если без опыта, со специалистом):

```bash
cd /srv/<проект>-prod && docker compose exec -T db sh -c 'dropdb -U "$POSTGRES_USER" --force "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
```

```bash
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner' < backups/<файл копии>.dump
```

Пользователь приложения и его права: если их нет после восстановления — выполнить
SQL из `initdb/01-app-user.sh` и `GRANT ... ON ALL TABLES` (часть 3 `server-setup.md`).

```bash
docker compose start app && curl -fsS http://127.0.0.1:<порт>/healthz
```

### На момент времени (PITR, WAL-G)

Восстанавливаем **в новый временный контейнер с пустым томом**, проверяем, потом
переключаем.

```bash
docker volume create pitr_data
```

```bash
docker run -d --name pitr --env-file .env.db --env-file .env.walg -v pitr_data:/var/lib/postgresql/data --entrypoint sleep <образ базы с wal-g> infinity
```

```bash
docker exec pitr sh -c 'wal-g backup-fetch "$PGDATA" LATEST && touch "$PGDATA/recovery.signal" && chown -R postgres:postgres "$PGDATA" && chmod 700 "$PGDATA"'
```

Время — в формате `2026-11-11 09:41:00+05` (с часовым поясом), на минуту раньше ошибки:

```bash
docker exec pitr sh -c "printf \"restore_command = 'wal-g wal-fetch %%f %%p'\nrecovery_target_time = '<ГГГГ-ММ-ДД ЧЧ:ММ:СС+ПП>'\nrecovery_target_action = 'promote'\n\" >> \"\$PGDATA/postgresql.auto.conf\""
```

```bash
docker exec -u postgres -d pitr postgres -D /var/lib/postgresql/data
```

Временная база запускается без `archive_mode`, поэтому ничего не пишет в хранилище
рабочей базы.

```bash
docker exec pitr sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select pg_is_in_recovery()"'
```

`f` — восстановление закончено. Проверь данные (`psql` во временную базу: нужная
строка на месте, число строк похоже на правду). Затем — выгрузка из временной базы
`pg_dump -Fc` и загрузка в рабочую, как в разделе выше, либо перенос тома — со специалистом.
Убрать временное: `docker rm -f pitr && docker volume rm pitr_data`.

**Звать человека:** всегда, если восстановление в эту базу ни разу не отрабатывалось
на учениях; если временная база не поднимается; если не уверены в моменте времени.

**Записать:** на какой момент восстановили, сколько данных потеряно (RPO по факту),
сколько длился простой (RTO по факту), что изменить в копиях.
