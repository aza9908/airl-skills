# Уровень продакшена: среды, проверки, миграции, инфраструктура в git, мощности

Этот файл — продолжение `server-setup.md`. Части 0–7 дают работающий продукт на одном
сервере. Здесь — как жить с ним дальше: тестовая среда перед боевой, выкладка только
после проверок, изменения базы без остановки, сервер, который собирается заново из git.

Что обязательно, а что по уровню из `airl-context` (`level`, `downtime_ok`, `data_loss_ok`):

| Что | Уровень 1 | Уровень 2 | Уровень 3 |
|---|---|---|---|
| Проверки в CI (линтер, тесты, `review_checks.sh`) перед выкладкой | да | да | да |
| Staging перед продакшеном | желательно | да | да, на отдельном сервере |
| Продакшен по метке и с одобрением | — | да | да |
| Миграции expand/contract, проверка на чистой базе в CI | да | да | да |
| Внешняя проверка `/healthz` и оповещение в Telegram | да | да | да |
| Метрики сервера (Prometheus, Grafana) | — | по желанию | да |
| Учёт ошибок (Sentry/GlitchTip) | желательно | да | да |
| PITR (восстановление на момент времени) | — | если `data_loss_ok: hour` | да |
| Инфраструктура в git + `bootstrap.sh` | да | да | да |

## 1. Среды: staging и production

**Staging** — копия продакшена с ненастоящими данными: сюда каждая версия попадает
автоматически, здесь её смотрят глазами. **Production** — то, чем пользуются люди:
сюда версия попадает только после staging, по метке и с одобрением.

### На одном сервере или на разных

| Вариант | Когда подходит | Риск |
|---|---|---|
| Один сервер, две папки | уровень 1–2, памяти от 4 ГБ, данные не особые | staging может съесть память продакшена — ставим ему лимиты |
| Два сервера | уровень 3, `downtime_ok: minutes/none`, особые данные (`sensitive`), нагрузочные тесты на staging | дороже, два сервера обслуживать |

Хаб: staging хаба — отдельная копия всего хаба (оболочка, прокси, тестовое хранилище);
сервисы отделов выкладываются в неё так же, как в боевой.

### Раскладка на сервере

```text
/srv/proxy/                      один прокси на сервер, оба домена
/srv/<проект>-staging/           свой compose-проект: своя база, свои секреты, свой порт
  docker-compose.yml  .env  .env.db  .env.app  .env.migrate  deploy.sh  backup.sh  backups/
/srv/<проект>-prod/
  (то же самое)
```

Правила:

- **Отдельный проект Docker Compose на каждую среду.** Имя проекта — в `.env`:
  `COMPOSE_PROJECT_NAME=<проект>-staging` / `<проект>-prod`. Тома, сети и контейнеры
  у сред разные, общая — только сеть `web` с прокси.
- **Разные базы и разные секреты.** Пароли staging и production не совпадают. Ключи
  внешних сервисов на staging — тестовые (песочница платёжной системы, тестовый бот).
- **Данные staging — синтетические или обезличенные.** Копию боевой базы с персональными
  данными на staging не переносим (см. `/airl-cybersecurity`).
- **Разные `APP_PORT`** (например, 3001 и 3000): порты на `127.0.0.1` общие для сервера.
- **Прокси различает среды по псевдониму в сети `web`**, а не по имени `app` — оно
  одинаковое в обоих проектах, и прокси попадал бы то в одну, то в другую среду.
- Staging закрыт паролем прокси и не индексируется поисковиками.

Фрагмент `docker-compose.yml` среды (остальное — как в части 3 `server-setup.md`):

```yaml
services:
  app:
    image: ghcr.io/<владелец строчными>/<репозиторий строчными>:${APP_TAG}
    restart: unless-stopped
    env_file: .env.app
    ports:
      - "127.0.0.1:${APP_PORT}:${APP_PORT}"
    networks:
      web:
        aliases: ["${APP_ALIAS}"]     # <проект>-staging или <проект>-prod
      internal:
    mem_limit: ${APP_MEM_LIMIT:-512m} # на staging — обязательно

  migrate:                            # запускается только из deploy.sh
    image: ghcr.io/<владелец строчными>/<репозиторий строчными>:${APP_TAG}
    profiles: ["tools"]
    env_file: .env.migrate            # DATABASE_URL владельца схемы (не пользователя приложения)
    command: ["sh", "scripts/migrate.sh"]
    depends_on:
      db:
        condition: service_healthy
    networks: [internal]
```

`.env` среды: `COMPOSE_PROJECT_NAME`, `APP_TAG`, `APP_PORT`, `APP_ALIAS`, `HEALTH_PATH`,
`APP_SERVICE=app`. Скрипт выкладки — `templates/deploy.sh`: он делает свежую копию,
запускает `migrate` из нового образа, перезапускает только приложение и откатывается,
если `/healthz` не ответил. Образ должен содержать `scripts/migrate.sh` и инструмент
миграций.

`/srv/proxy/conf/Caddyfile` для двух сред:

```caddyfile
<домен> {
    encode zstd gzip
    header Strict-Transport-Security "max-age=31536000"
    reverse_proxy <проект>-prod:<порт prod>
}

staging.<домен> {
    basic_auth {
        <логин> <хеш пароля из: docker compose exec caddy caddy hash-password>
    }
    header X-Robots-Tag "noindex, nofollow"
    reverse_proxy <проект>-staging:<порт staging>
}
```

DNS: A-запись `staging.<домен>` на тот же IP (или на IP второго сервера).

### Ключи выкладки

На каждую среду — **свой ключ** со своим ограничением `command=`: ключом staging нельзя
выложить в продакшен. Строки в `authorized_keys` пользователя сервера:

```text
command="/srv/<проект>-staging/deploy.sh \"$SSH_ORIGINAL_COMMAND\"",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding ssh-ed25519 AAAA... deploy-<проект>-staging
command="/srv/<проект>-prod/deploy.sh \"$SSH_ORIGINAL_COMMAND\"",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding ssh-ed25519 AAAA... deploy-<проект>-prod
```

### GitHub: окружения и одобрение

Человек делает руками (Settings репозитория):

1. **Environments → New environment → `staging`.** Секреты `STAGING_SSH_KEY`,
   `STAGING_HOST`, `STAGING_USER`; переменные `STAGING_URL`, `STAGING_KNOWN_HOSTS`.
2. **`production`** — то же с приставкой `PROD_`, плюс **Required reviewers** (один-два
   человека, кто отвечает за продукт) и **Deployment branches and tags → Selected →
   метки `v*`**.
3. **Branches → правило для `main`:** нельзя сливать без зелёной задачи «Проверки качества».

`STAGING_KNOWN_HOSTS` — строка из `ssh-keyscan -t ed25519 <IP>`, отпечаток которой
сверен с консолью провайдера: так CI не отправит метку на подменённый сервер.

**Тариф GitHub.** Окружения и обязательные проверяющие для приватных репозиториев
доступны не на всех тарифах — **уточните в документации GitHub в день настройки**.
Если недоступны: секреты с теми же именами заводятся как секреты репозитория (шаблон
работает и так, имена у сред разные), продакшен выкладывается только кнопкой
**Actions → ci-cd → Run workflow** с хешем версии, а создавать метки `v*` договорились
поручить одному-двум людям. Запиши это в `DEVOPS.md`.

### Как выглядит выпуск версии

```text
1. Код влит в main          → CI: проверки → образ → staging (сам)
2. Проверили на staging     → главное действие, вход под каждой ролью
3. git tag v1.4.0 && git push origin v1.4.0
4. CI ждёт одобрения        → ответственный нажимает Approve в Actions
5. Продакшен                → копия базы, миграции, новая версия, /healthz, проверка снаружи
```

Откат продакшена — одно из двух:

- **Actions → ci-cd → Run workflow**, `image_tag` = хеш прошлой версии (лежит
  в `/srv/<проект>-prod/.previous_tag` и в `deploy.log`);
- на сервере: `/srv/<проект>-prod/deploy.sh "$(cat /srv/<проект>-prod/.previous_tag)"`.

## 2. Ворота качества в CI

Шаблон — `templates/ci-cd.yml` → в репозиторий как `.github/workflows/ci-cd.yml`
(старый `deploy.yml` из части 7 после этого удаляется, чтобы не было двух выкладок).

| Ворота | Что проверяет | Остановит выкладку |
|---|---|---|
| Линтер | ошибки, которые видно без запуска | да |
| Проверка типов | обращения к полям и функциям не по объявлению | да |
| Миграции на чистой базе | все миграции применяются к пустой PostgreSQL в контейнере CI, повторный прогон ничего не меняет | да |
| Тесты | на базе после миграций | да |
| Аудит зависимостей | критические уязвимости в рабочих пакетах | да |
| `review_checks.sh` | ключи в коде и истории, опасные миграции, Dockerfile, порты в compose, `/healthz` | да, при блокирующих |
| Сборка образа + Trivy | критические уязвимости с исправлением в образе | да |
| Выкладка + `/healthz` снаружи | новая версия ответила; иначе сервер откатился сам | — |

**`scripts/review_checks.sh` копируется в репозиторий** из навыка `airl-code-review`
(`scripts/review_checks.sh` в его папке). Ссылка на папку навыка в CI не сработает:
там навыка нет. Обновили скрипт в навыке — скопируйте заново.

**`scripts/migrate.sh`** — одна команда миграций для CI, сервера и разработчика.
Читает `DATABASE_URL`. Примеры содержимого под инструмент проекта:

| Инструмент | Строка в `scripts/migrate.sh` |
|---|---|
| Prisma | `npx prisma migrate deploy` |
| Drizzle | `npx drizzle-kit migrate` |
| node-pg-migrate | `npx node-pg-migrate up` |
| Alembic | `alembic upgrade head` |
| Django | `python manage.py migrate --noinput` |
| Модули AIRL (`/airl-modules`) | `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f ...` в порядке из `MODULE.md` |

Начало файла всегда: `#!/bin/sh`, `set -eu`, проверка `: "${DATABASE_URL:?нужен DATABASE_URL}"`.

В хабе версия образа — из `airl.service.json` (см. «В хабе» в `server-setup.md`):
в задаче `build` добавьте шаг с `jq -r .version airl.service.json` и передайте его
в `APP_VERSION`.

## 3. Изменения базы без остановки и правила отката

Во время выкладки старая и новая версии кода какое-то время работают одновременно,
а откат возвращает старую. Поэтому **каждая миграция должна работать со старым кодом**.

**Expand → migrate → contract:**

1. **Expand** (расширить) — добавить новое: колонку без `NOT NULL`, таблицу, индекс
   `CONCURRENTLY`. Старый код этого не замечает. Выкладывается вместе с кодом, который
   ещё не зависит от нового.
2. **Migrate** (перейти) — новый код пишет в новое (или в оба места) и читает новое;
   старые строки переносит фоновая задача партиями.
3. **Contract** (сузить) — **следующим релизом**, когда старый код нигде не работает
   и перенос проверен: удалить старое, добавить `NOT NULL` и ограничения.

Пример — переименовать `phone` в `phone_e164`:

| Релиз | Миграция | Код |
|---|---|---|
| v1.5 | `ADD COLUMN phone_e164 text` | пишет в обе колонки, читает старую |
| — | фоновый перенос партиями | — |
| v1.6 | — | читает новую, пишет в обе |
| v1.7 | `DROP COLUMN phone` | только новая |

Безопасные замены для PostgreSQL:

| Опасно | Почему | Вместо этого |
|---|---|---|
| `ADD COLUMN ... NOT NULL` без `DEFAULT` | падает на таблице с данными | добавить без `NOT NULL` → заполнить → ограничение |
| `ALTER COLUMN ... SET NOT NULL` | проверка всей таблицы под блокировкой | `ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID`, потом `VALIDATE CONSTRAINT` |
| `CREATE INDEX` | блокирует запись на время построения | `CREATE INDEX CONCURRENTLY` отдельной миграцией вне транзакции |
| `ALTER COLUMN ... TYPE` | переписывает таблицу под блокировкой | новая колонка + перенос + переключение |
| `ADD FOREIGN KEY` | проверка всех строк под блокировкой | `NOT VALID`, потом `VALIDATE CONSTRAINT` |
| `UPDATE` всей таблицы | долгая блокировка, раздувание | партиями по 1000–10000 строк |
| `DROP` / `RENAME` | ломает работающий код и откат | только шагом contract |

В начале каждой миграции: `SET lock_timeout = '5s';` — если таблица занята, миграция
упадёт за 5 секунд, а не повесит продукт в очереди за блокировкой.

**Правила отката:**

- Откат — это **предыдущая версия кода** на уже расширенной базе. Он всегда возможен,
  если соблюдён expand/contract. `deploy.sh` делает его сам.
- **Миграции «вниз» (`down`) на продакшене не запускаем.** Ошибку в данных чиним
  новой миграцией вперёд.
- После шага contract кода, который знал старую схему, больше нет: откатиться можно
  только восстановлением копии (красная зона, `runbooks.md`). Поэтому contract — после
  недели спокойной работы новой версии и свежей проверенной копии.
- Один релиз — одно рискованное изменение. Миграцию данных и большую правку интерфейса
  не выкладываем вместе.
- В пятницу вечером, накануне Demo Day и без человека на связи продакшен не выкладываем.

## 4. Инфраструктура в git

Сервер должен собираться заново из репозитория и копии базы. Всё, что настроено
руками и нигде не записано, потеряется вместе с сервером.

```text
infra/
  bootstrap.sh            templates/bootstrap.sh — пользователь, SSH, ufw, Docker, fail2ban
  proxy/docker-compose.yml
  proxy/conf/Caddyfile
  env/staging/docker-compose.yml   .env.example
  env/prod/docker-compose.yml      .env.example
  deploy.sh               templates/deploy.sh — одинаковый для сред
  backup.sh               из части 5 server-setup.md (+ метрика из operations.md)
  server-checks.sh        templates/server-checks.sh
  notify-telegram.sh      templates/notify-telegram.sh
  crontab                 строки cron пользователя сервера
  monitoring/             templates/monitoring/* — уровень 2+
.github/workflows/ci-cd.yml
.github/dependabot.yml
```

Правила:

- **Секретов в `infra/` нет**: только `.env.example` с именами переменных. Значения —
  в файлах на сервере (права `600`) и в секретах GitHub.
- На сервере — клон репозитория только для чтения (ключ развёртывания GitHub, право
  read), например `/srv/infra`. Файлы сред и прокси — ссылки на файлы клона или копии,
  которые обновляются командой `git pull` и затем `cp`. Изменение настройки = PR → ревью →
  `git pull` на сервере → применить (Caddy: `caddy validate` и `caddy reload`).
- Проверка расхождений раз в месяц: `crontab -l | diff - /srv/infra/infra/crontab`,
  `diff /srv/infra/infra/proxy/conf/Caddyfile /srv/proxy/conf/Caddyfile`. Расхождение —
  либо в git, либо откатить на сервере.
- **Учение «новый сервер»** раз в квартал или перед Demo Day (уровень 2+): чистый
  сервер → `bootstrap.sh` → файлы сред → восстановление копии → выкладка метки.
  Засеките время: это и есть ваш реальный RTO (время восстановления). Запишите
  в `DEVOPS.md`.

`bootstrap.sh` безопасно запускать повторно: каждый шаг проверяет, сделан ли он.
Вход по паролю и под root он закрывает только с `--harden-ssh` и только если у
пользователя есть ключ, а итог проверяет через `sshd -T`.

## 5. Мощности и стоимость

Ориентиры для одного продукта на Docker Compose. **ПРЕДПОЛОЖЕНИЕ — проверить на
реальной нагрузке.** Цены — только с сайта провайдера в день выбора, в валюте клиента.

| Уровень | Что работает | Процессор / память / диск | Резервные копии |
|---|---|---|---|
| 1 | приложение + база, до ~100 пользователей | 1–2 vCPU / 2 ГБ / 40 ГБ SSD | `pg_dump` раз в сутки, вторая копия вне сервера |
| 2 | + staging, кэш, файлы, фоновые задачи | 2–4 vCPU / 4–8 ГБ / 80–160 ГБ NVMe | `pg_dump` + PITR при `data_loss_ok: hour` |
| 2 + метрики | + Prometheus, Grafana, Alertmanager | +1 ГБ памяти, +10–20 ГБ диска | — |
| 3 | несколько сервисов, простой недопустим | 2+ сервера или управляемые сервисы | PITR, реплика, учения |
| Хаб | оболочка, прокси, хранилище, 3–8 сервисов отделов | 4 vCPU / 8–16 ГБ / 160+ ГБ NVMe | PITR для хранилища |

Диск: база × 3 (сама база, копии на сервере, место под рост) плюс 10 ГБ под образы и логи.

**Когда нужен второй сервер** (хотя бы одно):

- память занята больше 80% или процессор больше 70% в часы пик неделю подряд,
  а оптимизация запросов не помогла;
- staging мешает продакшену даже с лимитами;
- `downtime_ok: minutes` или `none` — нужен запасной сервер или управляемая база;
- база перестала помещаться в память сервера, и запросы экранов замедлились;
- особые данные, а в той же машине крутятся тестовые сборки.

Первым на отдельный сервер обычно уезжает **база** (или в управляемую базу), вторым —
staging. Uptime Kuma — с первого дня на другом сервере или в облачном сервисе.

**Управляемая база или своя в контейнере:**

| | Управляемая база провайдера | Своя в Docker |
|---|---|---|
| Резервные копии и PITR | включаются галочкой | настраиваете и проверяете сами |
| Обновления и отказоустойчивость | делает провайдер | вы, вручную |
| Цена | заметно дороже того же объёма на VPS | дешевле |
| Где лежат данные | только регионы провайдера — сверить с «Страна и закон» | там, где ваш сервер |
| Контроль и расширения | ограничены | любые |
| Кому подходит | `maintainer: self-novice`, `downtime_ok: minutes` | есть кому обслуживать, бюджет ограничен |

При `maintainer: self-novice` и бюджете, который позволяет, рекомендуй управляемую базу
в разрешённом законом регионе: копии и восстановление — самое частое, что новички
делают неправильно.
