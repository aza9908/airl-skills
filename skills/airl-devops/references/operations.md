# Эксплуатация: логи, проверки, метрики, оповещения, ошибки, копии, защита сервера

Продолжение части 5–6 `server-setup.md`. Что из этого обязательно на каком уровне —
таблица в начале `production.md`.

## 1. Логи

**Формат — JSON одной строкой** на событие. Так логи можно искать и фильтровать,
а не читать глазами.

```json
{"time":"2026-11-11T09:12:03.120Z","level":"error","msg":"оплата не прошла","request_id":"b1f0…","user_id":42,"route":"POST /api/orders","duration_ms":812,"version":"3f2a9c1"}
```

Обязательные поля: `time` (UTC), `level`, `msg`, `request_id` (один на запрос, приходит
из заголовка `X-Request-Id` или создаётся), `version`. Можно: `user_id` (номер, не ФИО),
`route`, `duration_ms`, `status`.

**Нельзя:** ФИО, телефоны, e-mail, номера документов, адреса, тела запросов целиком,
токены, пароли, заголовок `Authorization`, cookie. Это требование `/airl-cybersecurity`.

Библиотеки: Node.js — `pino` (с `redact` для полей `req.headers.authorization`,
`*.password`, `*.phone`); Python — `structlog` или `logging` с JSON-форматтером.
Приложение пишет в стандартный вывод, а не в файлы: Docker сам их собирает.

**Ротация.** Логи контейнеров ограничены в `/etc/docker/daemon.json`
(`max-size 10m`, `max-file 5` — часть 6 `server-setup.md`, ставит `bootstrap.sh`).
Системный журнал — ограничить размер:

```bash
sudo mkdir -p /etc/systemd/journald.conf.d && printf '[Journal]\nSystemMaxUse=1G\n' | sudo tee /etc/systemd/journald.conf.d/airl.conf && sudo systemctl restart systemd-journald
```

Смотреть: `docker compose logs --tail 200 app`, поиск ошибок:
`docker compose logs --since 1h app | grep '"level":"error"'`.

Общий сбор логов (Loki + Grafana) — только уровень 2+ и если так решено
в `ARCHITECTURE.md` (`observability`).

## 2. Внешние проверки

Проверка снаружи — единственное, что заметит падение всего сервера.

- **Где:** облачный сервис (UptimeRobot, Better Stack и подобные) или **Uptime Kuma
  на другом сервере** (не на том, который проверяем). Uptime Kuma ставится одной
  строкой Docker и даёт страницу статуса.
- **Что проверять:** `https://<домен>/healthz` — каждую минуту, с ключевым словом
  `"status":"ok"`; `https://staging.<домен>/healthz` — раз в 5 минут, оповещение
  без звонка; срок сертификата — за 14 дней; в хабе — `/<id>/healthz` каждого сервиса.
- **Куда:** чат дежурных в Telegram (у Uptime Kuma есть встроенное оповещение Telegram).
- **Сколько ждать:** оповещение после 2–3 неудачных проверок подряд — иначе ложные
  тревоги от сетевых сбоев.
- Раз в месяц — **проверка оповещения**: остановить staging на минуту и убедиться,
  что сообщение пришло.

## 3. Метрики (уровень 2 и выше)

Шаблон — `templates/monitoring/`: node_exporter (процессор, память, диск, сеть),
Prometheus (хранит 30 дней), Alertmanager (оповещения в Telegram), Grafana (графики).
Все порты — только на `127.0.0.1`.

```bash
sudo mkdir -p /srv/monitoring/secrets /var/lib/node_exporter/textfile && sudo chown -R <пользователь>: /srv/monitoring
```

Скопируйте в `/srv/monitoring/` файлы из `templates/monitoring/`, подставьте имя
сервера и `chat_id`, токен бота человек вписывает сам в `secrets/telegram_token`
(права `600`). Затем:

```bash
cd /srv/monitoring && docker compose up -d && docker compose ps
```

Grafana — через туннель: `ssh -L 3000:127.0.0.1:3000 <пользователь>@<IP>`, затем
`http://localhost:3000`. При первом входе сменить пароль администратора; источник
данных — `http://prometheus:9090`; готовая панель для сервера — «Node Exporter Full»
(импорт по номеру из каталога Grafana).

**Метрика свежести копии.** Допишите в конец `backup.sh` (после `mv`):

```bash
METRICS=/var/lib/node_exporter/textfile
if [ -d "$METRICS" ] && [ -w "$METRICS" ]; then
  printf 'airl_backup_last_success_timestamp_seconds{project="%s"} %s\n' "<проект>-prod" "$(date +%s)" > "$METRICS/backup_<проект>.prom.tmp"
  mv "$METRICS/backup_<проект>.prom.tmp" "$METRICS/backup_<проект>.prom"
fi
```

Правило `BackupTooOld` в `alert-rules.yml` разбудит, если копии нет больше 26 часов.

Метрики приложения (число запросов, время ответа, ошибки) — `prom-client` для Node.js,
`prometheus_client` для Python, адрес `/metrics` только внутри сети `monitoring`.

## 4. Оповещения

| Что случилось | Важность | Куда | Кто реагирует |
|---|---|---|---|
| Продакшен не отвечает снаружи | критично | Telegram-чат дежурных, звонок по договорённости | дежурный сразу |
| Копии нет больше 26 часов | критично | чат дежурных | в тот же день |
| Диск больше 80%, память, контейнер перезапускается | предупреждение | чат дежурных | в рабочее время |
| Staging не отвечает | информация | чат разработки | разработчик |
| Выкладка откатилась | предупреждение | GitHub пишет автору; в чат — по желанию | автор выкладки |

**Уровень 1–2 без Prometheus:** `templates/notify-telegram.sh` (отправка) +
`templates/server-checks.sh` (диск, контейнеры, свежесть копии, память; одно и то же
оповещение не чаще раза в 6 часов, сообщает об исправлении). Установка — в шапке
`server-checks.sh`. Токен бота и id чата — в `/etc/airl/alert.env` с правами `600`,
человек вписывает сам:

```bash
sudo install -d -m 700 /etc/airl && sudo install -m 600 /dev/null /etc/airl/alert.env && sudo nano /etc/airl/alert.env
```

```bash
/usr/local/bin/notify-telegram "Проверка оповещения"
```

Бота создаёт человек у @BotFather, добавляет в чат дежурных; id чата — из
`https://api.telegram.org/bot<токен>/getUpdates` после любого сообщения в чат
(открывать в браузере человеку, в переписку не вставлять).

Правило: **у каждого оповещения есть раздел в `runbooks.md`**. Оповещение, на которое
никто ничего не делает, отключают или превращают в ежедневную сводку.

## 5. Учёт ошибок

Ловит необработанные ошибки с местом в коде, версией и числом пострадавших.

| | Sentry (облако) | GlitchTip (свой сервер) |
|---|---|---|
| Установка | регистрация, ключ (DSN) | Docker Compose, нужен PostgreSQL и ~1 ГБ памяти |
| Где данные | в регионах Sentry (США или ЕС) | там, где ваш сервер |
| Совместимость | — | принимает те же SDK Sentry |
| Когда | данные не персональные или закон разрешает передачу за рубеж | закон страны требует хранить данные в стране, особые данные |

**Где хранятся данные — решает раздел «Страна и закон» в `ARCHITECTURE.md`** (в хабе —
раздел 1 карты). Сообщение об ошибке может содержать персональные данные из запроса,
поэтому трансграничная передача — вопрос юристу, а не разработчику. Пока ответа
нет — GlitchTip на своём сервере в стране.

Настройка SDK в любом случае:

- `environment` — `staging` / `production`, `release` — `APP_VERSION`;
- `sendDefaultPii: false` (Python: `send_default_pii=False`), в `beforeSend` вычищать
  тело запроса, cookie и заголовки;
- DSN — в `.env.app`, на staging и production разные проекты;
- оповещение о новой ошибке — в чат разработки.

## 6. Резервные копии и восстановление на момент времени

Схема выбирается из `airl-context`: `data_loss_ok` задаёт RPO (сколько данных можно
потерять), `downtime_ok` — RTO (сколько можно простаивать).

| `data_loss_ok` | RPO | Схема |
|---|---|---|
| `day` | до 24 ч | `pg_dump` раз в сутки (часть 5 `server-setup.md`) + вторая копия вне сервера |
| `hour` | до 5–15 мин | `pg_dump` раз в сутки **+ архив журнала WAL** (PITR) |
| `none` | ~0 | управляемая база с репликой или специалист: за рамками курса, скажи прямо |

| `downtime_ok` | RTO | Что нужно |
|---|---|---|
| `hours` | 2–8 ч | копия вне сервера + `bootstrap.sh` + отработанное учение «новый сервер» |
| `minutes` | до 30 мин | запасной сервер или управляемая база, восстановление отрепетировано |
| `none` | ~0 | отказоустойчивый кластер — специалист |

Запиши выбранные RPO и RTO в `DEVOPS.md` и скажи человеку честно, если бюджет их
не обеспечивает.

### PITR через WAL-G (для критичных баз)

PostgreSQL пишет каждое изменение в журнал WAL. Если непрерывно отправлять журнал
в хранилище и раз в сутки делать полную копию, базу можно восстановить **на любую
секунду** между копиями — например, на минуту до ошибочного `DELETE`.

Нужно: объектное хранилище (S3-совместимое) **в стране, которую требует раздел
«Страна и закон»**, отдельный бакет, ключ доступа только к нему. Альтернатива WAL-G —
pgBackRest (умеет то же, сложнее в настройке, сильнее в больших базах).

1. Свой образ базы с WAL-G (`infra/postgres/Dockerfile`). Версию и файл релиза для
   Linux amd64 возьмите со страницы релизов github.com/wal-g/wal-g, сверьте контрольную
   сумму; основная версия PostgreSQL — та же, что сейчас:

```dockerfile
FROM postgres:16
ARG WALG_URL
ARG WALG_SHA256
ADD --checksum=sha256:${WALG_SHA256} ${WALG_URL} /tmp/wal-g.tar.gz
RUN tar -xzf /tmp/wal-g.tar.gz -C /usr/local/bin && mv /usr/local/bin/wal-g-pg-* /usr/local/bin/wal-g && chmod +x /usr/local/bin/wal-g && rm /tmp/wal-g.tar.gz
```

2. В `docker-compose.yml` у службы `db`: образ из шага 1, второй файл окружения
   `env_file: [.env.db, .env.walg]`, где `.env.walg` (права `600`) содержит `WALG_S3_PREFIX=s3://<бакет>/<проект>-prod`,
   `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT`, `AWS_REGION`,
   `WALG_COMPRESSION_METHOD=brotli`, `WALG_LIBSODIUM_KEY` — ключ шифрования, хранится
   ещё и вне сервера: без него копия бесполезна. Команда запуска:

```yaml
    command:
      - postgres
      - -c
      - archive_mode=on
      - -c
      - archive_command=wal-g wal-push %p
      - -c
      - archive_timeout=60
```

   Смена `archive_mode` требует перезапуска базы — жёлтая зона: свежий `pg_dump`,
   окно обслуживания, «да».

3. Полная копия каждую ночь и хранение 7 полных копий (cron пользователя сервера):

```text
30 2 * * * cd /srv/<проект>-prod && docker compose exec -T db sh -c 'wal-g backup-push "$PGDATA"' >> backups/walg.log 2>&1
30 4 * * 0 cd /srv/<проект>-prod && docker compose exec -T db wal-g delete retain FULL 7 --confirm >> backups/walg.log 2>&1
```

4. Проверка, что журнал уходит: `docker compose exec db wal-g backup-list` — свежая
   копия есть; `docker compose exec db psql -U "$POSTGRES_USER" -c "select last_archived_time, failed_count from pg_stat_archiver"` —
   время свежее, ошибок не прибавляется.

`pg_dump` раз в сутки **не отключаем**: это независимая вторая линия, и её проще
восстановить.

Восстановление на момент времени — `runbooks.md`, раздел 6.

### Учения по восстановлению

| Что | Как часто | Где |
|---|---|---|
| `pg_dump` → временный контейнер, таблицы и число строк | раз в месяц и после любого изменения схемы копий | на сервере, рядом с рабочей базой |
| PITR на заданную минуту → временный контейнер | раз в квартал (уровень 2+), до Demo Day | на сервере или отдельном |
| «Новый сервер»: `bootstrap.sh` + восстановление + выкладка | раз в квартал (уровень 2+) | новый временный сервер |

Дату, длительность и результат каждого учения записывай в `DEVOPS.md`. Копия, которую
не восстанавливали больше 3 месяцев, считается непроверенной.

## 7. Защита сервера

| Мера | Где сделано | Проверка |
|---|---|---|
| Вход только по ключу, root закрыт | часть 1, `bootstrap.sh --harden-ssh` | `sudo sshd -T \| grep -Ei '^(passwordauthentication\|permitrootlogin)'` → `no` |
| fail2ban для SSH | `bootstrap.sh` | `sudo fail2ban-client status sshd` |
| Автообновления безопасности | часть 1, `bootstrap.sh` | `systemctl status unattended-upgrades` |
| Перезагрузка после обновления ядра | раз в месяц в окно обслуживания | есть файл `/var/run/reboot-required` — пора |
| Ограничение логов Docker | часть 6, `bootstrap.sh` | `docker info --format '{{.LoggingDriver}}'` и `daemon.json` |
| Наружу только 22, 80, 443 | часть 2 | `sudo ufw status`, `nc -zv <IP> 5432` снаружи — отказ |
| Сканирование образа (Trivy) | `ci-cd.yml`, задача build | критические уязвимости останавливают выкладку |
| Обновления зависимостей | `templates/dependabot.yml` → `.github/dependabot.yml` | PR от Dependabot раз в неделю, сливаются после зелёного CI и staging |
| Права приложения в базе — без администратора | часть 3 | `.env.app` не содержит пароля `POSTGRES_USER` |

Раз в неделю (или в задаче CI по расписанию) — сканирование уже работающих образов:
`docker run --rm aquasec/trivy:<версия> image --severity CRITICAL --ignore-unfixed <образ>:<метка>`.
Уязвимости появляются и в старых образах.

### Ротация секретов

Ведите в `DEVOPS.md` таблицу **без значений**:

| Секрет | Где хранится | Кто владелец | Последняя замена | Как часто |
|---|---|---|---|---|
| Пароль пользователя приложения в базе | `.env.app`, `.env.db` | [имя] | ГГГГ-ММ-ДД | 180 дней |
| Ключ выкладки prod | `authorized_keys`, секрет GitHub `PROD_SSH_KEY` | [имя] | | 365 дней |
| Ключ внешнего API | `.env.app` | | | по правилам сервиса |
| Токен бота оповещений | `/etc/airl/alert.env` | | | при уходе сотрудника |

Менять сразу, вне графика: утечка или подозрение (`runbooks.md`, раздел 5), уход
человека, у которого был доступ, ключ попал в git, в чат или на скриншот.

Порядок замены любого секрета — **сначала новый, потом отзыв старого**:

1. Создать новое значение (кабинет сервиса, `ssh-keygen`, генератор паролей).
2. Вписать его там, где читает продукт: `.env.app` на сервере (человек сам, права `600`)
   и/или секрет в GitHub (окружение staging, затем production).
3. Перезапустить только то, что читает секрет: `docker compose up -d --no-deps app`.
4. Проверить: `/healthz`, главное действие, интеграция работает.
5. **Отозвать старое значение** в кабинете или удалить строку из `authorized_keys`.
6. Записать дату в таблицу.

Пароль пользователя приложения в базе:

```bash
docker compose exec db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\password <пользователь приложения>"
```

Команда спросит новый пароль дважды и не покажет его на экране. Затем новый пароль —
в `DATABASE_URL` в `.env.app` и `APP_DB_PASSWORD` в `.env.db`, перезапуск приложения,
проверка `/healthz`. Между сменой пароля и перезапуском приложение не сможет открыть
новые соединения к базе — делайте в тихое время.
